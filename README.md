# webvnc · 网页端远程桌面

在被控端运行一个单文件程序，其他设备用浏览器打开就能**看到这台电脑的桌面并直接操作它**（移动鼠标、点击、滚动、敲键盘、输入中文）。

- 后端 Go，前端 Vue3 + TypeScript，构建产物是**一个可执行文件**，前端资源全部内嵌，不依赖任何外部文件
- 屏幕采集、输入注入全部用系统原生接口实现（Windows 走 `gdi32` / `user32`，Linux 走 X11 协议），**纯 Go，不需要 CGO**
- 通信走 WebSocket：画面和声音**各一条连接**，下行 JPEG 画面帧与 PCM 音频，上行 JSON 输入事件
- **能听到远程电脑的声音**（Windows）。默认关闭，点一下工具栏才开——这不是偏好，是浏览器的自动播放策略要求必须先有用户手势

> **平台支持：Windows 与 Linux（X11）。** 两个平台的画面与输入都是完整实现，差别在声音与剪贴板：
> Linux 版本目前**没有**声音采集，剪贴板接口返回"不支持"而不是静默失败。
> 具体到发行版、桌面环境、Wayland 的注意事项见[第 2.5 节](#25-平台支持)。

> **本文是查阅手册**（参数、协议、FAQ、限制）。
> 想先看全局：架构、每一层的关键决定及其代价、坑按**失败类型**的归类 → [`工程总结.md`](工程总结.md)。
> 想看逐轮改动的完整过程与原始记录 → [`开发札记.md`](开发札记.md)。

## 1. 快速开始

```powershell
# 1. 构建（首次需要装前端依赖）
.\build.ps1

# 2. 运行
.\webvnc.exe
```

启动后终端会打印：

```
  webvnc 0.1.0  远程桌面服务已启动
  ────────────────────────────────────────────
  监听地址   :8339
  屏幕分辨率 1920 x 1080
  声音       开启  系统回环采集，未压缩 PCM 约 1.4-1.5 Mbps
  访问口令   k7m2p9xr4w   (本次随机生成)
  本机访问   http://127.0.0.1:8339  ·  http://[::1]:8339
  局域网访问 http://192.168.1.100:8339
  IPv6 访问  http://[2001:db8:abcd:1234:5678:9abc:def0:1234]:8339
  ────────────────────────────────────────────
  安全提示: 请勿直接暴露到公网，建议配合内网 / VPN / 反向代理使用。
  按 Ctrl+C 退出。
```

在**另一台设备**（手机 / 平板 / 另一台电脑）的浏览器里打开 `http://192.168.1.100:8339`，输入上面的口令即可。

> 未指定 `-password` 时，口令每次启动随机生成并打印在日志里。想固定口令就运行 `.\webvnc.exe -password 你的口令`。
>
> 上面所有地址是**并列可选**的，随便挑一个能连通的用。有 IPv6 就在地址两边加方括号
> （`http://[2001:db8:...]:8339`），这是 URL 标准要求，不是本程序的特殊语法。详见[第 3.2 节](#32-ipv6-访问)。
>
> 传了 `-tls-cert` / `-tls-key` 时这些地址会全部变成 `https://`，并且**只有证书覆盖的那个域名能正常打开**，
> 用 IP 打开会报证书错误——届时更推荐直接用域名。详见[第 5.1 节](#51-直接启用-httpswss)。

## 2. 构建

### 2.1 环境要求

| 依赖 | 版本 | 说明 |
| --- | --- | --- |
| Go | 1.22+ | 需要 `embed` 包 |
| Node.js | 18+ | 只在构建前端时需要，运行二进制不需要 |
| X11 运行库 | Linux 运行期 | 只需要 `libX11.so` 存在于系统里（Ubuntu 桌面版自带）；**构建时不需要**，也不需要 `-dev` 包 |

**不需要 C 编译器。** 屏幕采集和输入注入都用 `syscall` 直接调用系统接口——Windows 是 `user32.dll` / `gdi32.dll`，Linux 是 X11 协议（走 `github.com/jezek/xgb` 的纯 Go 实现）。两个平台构建时都是 `CGO_ENABLED=0`，产物是静态单文件。

### 2.2 一键构建

两个平台的脚本**一一对应**，做的事完全相同：`npm install` → `npm run build`（含 `vue-tsc` 类型检查）→ `go build -trimpath -ldflags "-s -w -X main.version=..."`。

```powershell
.\build.ps1                           # Windows，输出 webvnc.exe
```
```bash
./build.sh                            # Linux / Ubuntu，输出 webvnc
```

常用变体（左边 Windows，右边 Linux）：

```powershell
.\build.ps1 -SkipInstall              # ./build.sh --skip-install     前端依赖已装好
.\build.ps1 -SkipFrontend             # ./build.sh --skip-frontend    只重新编译 Go
.\build.ps1 -Output webvnc-dev.exe    # ./build.sh -o webvnc-dev      指定输出文件名
.\build.ps1 -Version 0.2.0            # ./build.sh --version 0.2.0    注入版本号
```

两边用同样的参数实测都是 **约 7.3 MB** 的单文件（Linux 7.34 MB、Windows 7.28 MB）。只改了 Go 代码时用 `-SkipFrontend` / `--skip-frontend`，省掉整轮前端构建——但要记住它的代价，见[第 7 节](#帧间压缩h264)那个黑屏坑。

> **Ubuntu 上没有桌面会话时**（服务器 / 容器 / CI），`build.sh` 会在 `DISPLAY` 为空时打印一句提示，但**照常构建**——编译不需要 X 服务器，只有**运行**才需要。跑之前先起一个虚拟的：
> ```bash
> sudo apt install xvfb
> Xvfb :99 -screen 0 1280x800x24 &
> DISPLAY=:99 ./webvnc -password 你的口令
> ```

### 2.3 手动构建（两步，顺序不能颠倒）

```bash
# 第一步：构建前端，生成 frontend/dist
cd frontend
npm install
npm run build
cd ..

# 第二步：编译 Go，此时 dist 会被 //go:embed 打进二进制
CGO_ENABLED=0 go build -o webvnc .
```

Windows 上完全一样，只是最后一行换成 `go build -o webvnc.exe .`（`CGO_ENABLED=0` 由 `build.ps1` 设，手动构建时也可以不管——两个平台都没有 cgo 依赖）。

> **顺序很重要。** `//go:embed frontend/dist` 是在**编译期**读取 `dist` 目录的。
> 如果先跑 `go build`，会因为找不到 `frontend/dist` 而直接编译失败；
> 如果改了前端却忘了重新 `npm run build`，二进制里打包的还是旧页面。

### 2.4 前端开发模式

调试界面时不必每次重新编译二进制。先跑起后端，再启动 Vite 开发服务器：

```bash
# 终端 1（Windows 下是 .\webvnc.exe）
./webvnc -addr 127.0.0.1:8080 -password dev

# 终端 2
cd frontend
npm run dev        # 打开 http://localhost:5173，已配置 /api 和 /ws 代理到 8080
```

> **这里的 8080 是刻意的，不是默认端口。** 默认是 8339，而 `vite.config.ts` 里的开发代理写死指向
> `127.0.0.1:8080`——所以开发模式下必须显式用 `-addr 127.0.0.1:8080` 启动后端，否则页面能打开但
> `/api` 和 `/ws` 全部连不上。改代理配置或改这条命令都行，两者保持一致即可。

### 2.5 平台支持

| | Windows | Linux |
| --- | --- | --- |
| 抓屏 | GDI（`BitBlt` + DIB 段） | X11（MIT-SHM，不可用时回退 `GetImage`） |
| 鼠标 / 键盘注入 | `SendInput` | XTEST（`XTestFakeInput`） |
| 中文等任意文本输入 | `KEYEVENTF_UNICODE` | 动态重映射一个临时 keycode |
| 帧间编码（H.264） | Media Foundation | **无**，自动退回帧内 JPEG |
| 声音采集 | WASAPI 回环 | **无**，接口返回"不支持" |
| 剪贴板 | `CF_UNICODETEXT` | **无**，接口返回"不支持" |
| 构建脚本 | `build.ps1` | `build.sh` |

Windows 侧的声采与剪贴板是既有一期的实现；Linux 侧这两项是**明确的空缺**，而不是"有但没测"。
调用它们会拿到 `ErrUnsupportedAudio` / `ErrUnsupportedClipboard` 哨兵错误，页面上是明确提示，
不会静默地什么都不做。

**具体到启动横幅**：`-audio` 默认是开，但一个没有声音后端的平台没法兑现它。
所以 Linux 上横幅会直接写 `声音 不支持`，并且 `/ws/audio` 路由**返回 404**——
客户端对"服务端把这个功能关了"是有专门处理的（停止重试并说明），
比让用户点一下按钮、等四次重连、再面对一片安静要好得多。
判断由 `server.AudioSupported()` 给出，按平台编译。同一件事也体现在 `-h` 里：
第一行的平台名、示例里的可执行文件名、`-audio` 的说明也都是按平台取值的，
所以在 Linux 上不会看到"这台 Windows 电脑"或者 `webvnc.exe`。

**Linux 的运行期要求：**

```bash
# Ubuntu/Debian 桌面版什么都不用装；只有裸机 / 容器里跑才需要：
sudo apt install libx11-6          # 运行二进制只需要这个（不是 -dev）

# 完全没有桌面环境时，可以起一个虚拟 X 服务器把画面接过去：
sudo apt install xvfb
Xvfb :99 -screen 0 1280x800x24 &
DISPLAY=:99 ./webvnc -password 你的口令
```

> **Wayland 会话下画面是不完整的。** 程序连的是 X 服务器，在 Wayland 桌面上那意味着
> **XWayland**——它只能看到跑在 XWayland 里的 X11 程序。GNOME 桌面本身、多数终端和浏览器
> 都是 Wayland 原生的，**不会出现在画面里**。启动时会打印一条警告说明这一点。
> 鼠标键盘注入不受影响（XTEST 在 XWayland 下正常工作）。
> 要完整的 Wayland 抓屏需要走 `xdg-desktop-portal` / PipeWire，那是二期的事。

> **MIT-SHM 与远程显示。** 画面通路优先走 MIT-SHM（共享内存），整屏像素不经过 X socket。
> 但当 `DISPLAY` 指向一台**远端** X 服务器（`ssh -X`、XDMCP）时，X 服务器的 `shmget`
> 在对面没有意义，协商会失败——程序会打印一条警告并自动退化为 `GetImage`，
> 功能正常但每帧多一次整屏的 socket 传输。

## 3. 运行参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `-addr` | `:8339` | 监听地址。`:8339` 同时监听 IPv4 与 IPv6 的所有网卡；`127.0.0.1:8339` / `[::1]:8339` 只允许本机访问。IPv6 地址必须加方括号 |
| `-password` | 随机生成 | 访问口令。留空则每次启动随机生成 10 位口令并打印 |
| `-fps` | `15` | 屏幕推送帧率，上限 60 |
| `-quality` | `65` | JPEG 质量 (1-100)。调低可显著降低带宽 |
| `-codec` | `auto` | 画面压缩方式：`auto`=优先**帧间**（H.264），不可用时自动退回**帧内**（JPEG）；`h264`=只用帧间，不可用则启动失败；`jpeg`=只用帧内。详见[第 7 节「帧间压缩」](#帧间压缩h264) |
| `-scale` | `1.0` | 画面缩放比例，取值 (0, 1]。`0.75` 表示缩到 75% 再编码 |
| `-max-clients` | `8` | 同时连接的客户端上限，`0` 表示不限 |
| `-log-level` | `info` | `debug` / `info` / `warn` / `error`。`debug` 会额外显示 X11 客户端库的诊断（例如找不到 `.Xauthority`——Xvfb / 容器里很常见，连接照常建立） |
| `-log-format` | `text` | `text` / `json`。所有输出都走这个格式，包括 X11 库的，不会有裸文本行混进来 |
| `-max-bitrate` | `0` | 码率上限，`0` 表示不限。支持 `800k` / `2M`，纯数字单位是 kbps。详见下方「码率控制」 |
| `-priority` | `fps` | 超预算时的取舍：`fps`=先降画质保帧率，`quality`=先降帧率保画质 |
| `-min-quality` | `30` | 码率控制可降到的最低 JPEG 质量 |
| `-min-fps` | `5` | 码率控制可降到的最低帧率 |
| `-static-skip` | `true` | 画面无变化时跳过编码与发送。排查问题时可用 `-static-skip=false` 关闭 |
| `-audio` | `true` | 是否提供声音采集能力。`false` 时 `/ws/audio` 返回 404，服务端完全不采集声音。详见[第 3.3 节](#33-声音与带宽) |
| `-view-only` | `false` | **直播模式**：所有客户端只能看画面、听声音，不能操作这台电脑。开关在服务端，客户端无法解除。详见[第 5.4 节](#54-直播模式只读广播) |
| `-tls-cert` | 空 | TLS 证书链文件（PEM）。与 `-tls-key` 同时给出时改用 `https` / `wss` 提供服务；两者都不给就是明文 HTTP。只给一个会启动失败 |
| `-tls-key` | 空 | TLS 私钥文件（PEM），与 `-tls-cert` 配对。**这是机密文件，不要泄露或随程序分发** |

### 3.1 带宽调优

**画面不动就不占带宽。** 每一帧都会与上一帧已发送的像素逐字节比较，完全一致就既不编码也不发送——
一个静止的桌面带宽是 **0**，同时省掉编码的 CPU。比较在第一个不同的字节处短路返回，所以「画面在动」
这种常见情况的额外开销几乎为零。鼠标指针移动**不会**被算作变化：GDI 的 `BitBlt` 本来就不合成光标，
这也是为什么远程画面里看不到对方的鼠标指针。

需要注意，闪烁的光标、走字的时钟、任务栏动画都会让整帧判定为「有变化」，此时带宽不会归零。想确认
当前状态，看界面状态条上的「静止」标记，或 `GET /api/stats` 的 `idle` 字段。

**码率上限自动降级。** 设置 `-max-bitrate` 后，服务端每秒统计一次**实际发到 socket 的字节数**
（不是编码产出——队列满而被丢弃的帧不计入），超出预算就自动降级：

- `-priority fps`（默认）：先降画质，画质降到 `-min-quality` 后开始降帧率；
- `-priority quality`：先降帧率，帧率降到 `-min-fps` 后开始降画质；
- 低于预算的 60% 会按相反顺序逐步恢复；60%~85% 之间保持不变（迟滞带，避免来回抖动）。

> **上限的语义：** 指**服务端总出口**。多个客户端收到的是同一份编码帧，所以总出口 ≈ 每客户端码率 × 客户端数，
> 而这个上限约束的是**总和**。3 台设备同时看，上限 2 Mbps 就是三台加起来 2 Mbps。
> 它是**软上限**：突发画面会让它短暂超出，通常 2~3 秒内收敛回目标区间。

> **帧间模式下 `-quality` / `-min-quality` 不起作用。** H.264 编码器不接受 JPEG 质量参数，它有自己的
> 码率控制，所以超预算时控制器只有帧率这一个旋钮可压，上面那条降级顺序实际只剩下后半段。
> 真正管用的是一个足够低的 `-max-bitrate`：见[第 7 节「帧间压缩」](#帧间压缩h264)的实测数字，
> 同一段素材上帧间的码率本来就比帧内低得多。

降级到底仍然超预算时（`/api/stats` 的 `atFloors` 为 `true`），日志会给出一次告警。这种情况只能靠
`-scale` 解决——它是唯一能减少「要编码的像素数量」的开关，也是码率控制器够不着的那个旋钮。

```powershell
.\webvnc.exe -max-bitrate 2M                      # 总出口限制 2 Mbps，默认帧率优先
.\webvnc.exe -max-bitrate 2M -priority quality    # 同样限额，但优先保住画质
.\webvnc.exe -scale 0.75 -quality 50 -fps 10      # 手动固定参数，不用自适应
.\webvnc.exe -codec jpeg                          # 退回帧内 JPEG（默认是 auto）
```

**实测参考。** 1440×900 桌面、`-quality 65`、`-max-bitrate 2M -priority quality -min-fps 4`：
未限速时约 7 Mbps / 15fps；控制器收敛后稳定在约 2.3 Mbps / 4fps，JPEG 质量自始至终保持 65 不变
（正是 `quality` 优先的含义），并打印一次「已达下限」告警。静止画面的带宽为 **0 字节/秒**——
这一项由 `server/ws_stream_test.go` 以确定性方式断言（静止 1 帧 → 运动 35 帧 → 再次静止 0 帧）。

**性能说明。** 没有任何客户端连接时，采集循环完全跳过截图和编码，进程几乎不占 CPU。有客户端时，
编码耗时由 CPU 决定，`-fps` 只是上限，达不到会自动降速。

### 3.2 IPv6 访问

**IPv6 默认就是开着的**，不需要加任何参数。默认的 `-addr :8339` 是一个**双栈监听**：同一个端口同时
接受 IPv4 和 IPv6 连接，IPv4 客户端不会被冷落，IPv6 客户端也不用改配置。

| 想要的效果 | `-addr` 写法 |
| --- | --- |
| 双栈，监听所有网卡（默认） | `:8339` 或 `[::]:8339` |
| 只监听 IPv4 | `0.0.0.0:8339` |
| 只允许本机，IPv4 | `127.0.0.1:8339` |
| 只允许本机，IPv6 | `[::1]:8339` |
| 只监听某个具体的 IPv6 地址 | `[2001:db8:abcd:1234::1]:8339` |

> **方括号是 URL 的语法，不是本程序的规定。** IPv6 地址里本来就用冒号分隔，和 `主机:端口` 的分隔符
> 撞车，所以 URL 标准规定 IPv6 必须写成 `http://[地址]:端口`。少了方括号浏览器会解析失败。
> 浏览器地址栏里直接敲 `http://[::1]:8339` 即可。

**启动横幅会按实际绑定情况列出可用地址。** 打印哪些行取决于 `-addr`：绑到 `127.0.0.1` / `[::1]` 这种
只回环的地址时，就只打印本机访问地址，不会列出局域网和 IPv6 的地址（列了也连不上）；绑到通配地址时，
局域网 IPv4 地址和全局 IPv6 地址都会列出来，各挑一个能通的用。

**链路本地地址（`fe80::` 开头）不会列出来。** 它必须带上网卡的作用域标识才能用，写成
`http://[fe80::1%2516]:8339` 这种形式（`%25` 是 `%` 在 URL 里的转义）。横幅里省掉它是因为那个
`%16` 的序号每台机器都不一样，列出来反而会让人抄错。局域网内优先用上面列出的全局 IPv6 地址。

**防火墙规则对两个协议族都生效。** [第 10 节](#10-常见问题)给的
`New-NetFirewallRule` 命令没有指定协议族，所以 IPv4 和 IPv6 入站会一起放行，不需要为 IPv6 再加一条。

> ⚠️ **公网可路由的 IPv6 地址要格外当心。** 很多宽带运营商（如中国电信的 `240e::/20`）会给每台设备
> 直接分配**公网可达**的 IPv6 地址，而且常常没有 NAT 挡在中间——这和 IPv4 时代「内网有 NAT 保护」的
> 直觉完全不同。如果路由器没有拦截入站连接，外网就能直接访问到这个服务。启动时若检测到公网 IPv6，
> 横幅会额外打印一段提醒；请务必设置强口令，或改用 `-addr` 限制监听范围。详见[第 5 节](#5-安全须知务必阅读)。

### 3.3 声音与带宽

**采的是「系统在放什么」，不是「麦克风听到什么」。** 服务端通过 WASAPI 对**默认播放设备**做**回环采集**
（loopback），也就是把这台电脑正在往外放的声音原样截一份发给浏览器——在线视频、音乐、游戏、系统提示音
都能听到。麦克风不在范围内。

**不压缩。** 传输格式是未压缩的 16-bit PCM，只做格式转换不做编码：`CGO_ENABLED=0` 且不引第三方依赖，
纯 Go 没有可用的 Opus/AAC 编码器；而且往浏览器送 Opus 还得再套一层 MSE + WebM 封装。代价是带宽恒定在
音频本身的码率上，好处是**数字层面完全无损**，音乐一点不打折。

采样率与声道数**跟着设备走**，服务端在连接建立时把实际格式告诉浏览器：

| 设备混音格式 | 线上码率 | 每个 20ms 包 | `-max-bitrate 2M` 时留给视频 |
| --- | --- | --- | --- |
| 44.1 kHz 立体声（最常见） | 1411 kbps | 3528 字节 | 约 589 kbps |
| 48 kHz 立体声 | 1536 kbps | 3840 字节 | 约 464 kbps |

**声音要从 `-max-bitrate` 里扣。** 上一节说过这个上限约束的是**服务端总出口**；声音是一路恒定的码流，
如果它不进预算，那个承诺就被悄悄破坏了（设 2M 实际跑出 3.5 Mbps）。所以视频控制器的目标改成

```
视频目标 = max(0, MaxBitrate − 音频标称码率)
```

音频用**标称**码率而不是实测码率来扣：PCM 是恒定码率，没有可测量的波动，用固定值扣可以避免控制器追着
音频统计抖动来回调整。**没开声音时（没有音频客户端）音频标称码率为 0，一切与从前完全一样。**

> ⚠️ **开了声音，画面就要让路。** 这正是上面那张表的意思：`-max-bitrate 2M` + 44.1 kHz 声音，
> 视频只剩约 589 kbps，画质和帧率都会明显下降。想同时要有声音和可看的画面，把上限提到
> `-max-bitrate 4M` 之类，或者用 `-scale 0.75` 先把要编码的像素数量降下来。
>
> 音频单独就超预算时（如 `-max-bitrate 1M` + 1.4 Mbps 的声音），日志会给出一次告警，
> 与「已降到下限仍超预算」的告警同样处理。

**安静时不发，也不采。** 连续约 200 ms 没有声音就停止发送，重新有声音立刻续传（恢复的第一个包会有
一次极短的缓冲欠载，是这条策略的已知代价）。更彻底的是：**一个音频客户端都没有时，服务端根本不打开
采集设备**——不开声音的会话在声音这块的 CPU 占用是零。

**声音到达的速率比播放的速率略低，浏览器按实测速率回放。** 采集设备、服务端的打包节拍、
浏览器这边的声卡是三个各自独立的时钟，采样率只是各自的标称值。本机实测（音源连续、机器空闲）：

| 测点 | 实测速率 |
| --- | --- |
| 采集设备本身（不进服务端循环） | 99.94% |
| 端到端到浏览器（60 秒 2983 / 3000 个包） | **99.42%** |

两个数都是「相对真实时间」，不是相对标称采样率。设备本身几乎是准的；**端到端稳定少约 0.6%**，
即每秒少 5 ms 左右的声音——小到不足以表现为「丢包」，但足够让 100 ms 的抖动余量以约 5 ms/s 流失，
**连续播放约 20 秒后就见底**。此后每个包一到就播，再无余量可失，网络稍有抖动就是一次爆音。

所以 `AudioPlayer` 不是按标称采样率回放，而是统计实际到达的帧率并把回放速率调成与它一致
（限制在 ±1% 以内，即最多 1% 的音高偏移，听不出来，也远大于实测需要的 0.6%）。这样余量能长期
维持在设定值上，网络抖动才有东西可吸收。这样做还有个好处：**它不关心这 0.6% 到底出在哪一环**，
换一台机器、换一块声卡、换一个采样率都自动跟上。

> 顺带一提，最初测到的「63 秒里少 362 ms」是个**测量错误**：当时桌面上放的内容本身有断续，
> 量到的是音源的空档，不是采集的时钟。换成连续音源后设备侧立刻回到 99.94%。真正的端到端缺口
> 是上表那 0.6%，量级更小，原因仍未完全定位（采集侧只有 0.06%，其余在服务端循环到浏览器之间）。

**只采默认播放设备。** 机器上挂着多个渲染端点时（HDMI、虚拟声卡、串流设备等），采的是 Windows 里
设成**默认**的那一个。如果默认被 Steam Streaming Speakers 之类的虚拟设备占着，就会采到一片安静——
这种情况先去「设置 → 系统 → 声音」把默认输出改回真实的扬声器/耳机。

```powershell
.\webvnc.exe                          # 默认提供声音能力，浏览器里点一下才出声
.\webvnc.exe -audio=false             # 完全关闭：/ws/audio 返回 404，服务端不采集
.\webvnc.exe -max-bitrate 4M          # 想声音和画面兼得，就把总出口上限抬高
```

| 操作 | 方式 |
| --- | --- |
| 控制鼠标 | 直接在画面上移动、左键/右键/中键点击、滚轮滚动 |
| 键盘输入 | 桌面：直接敲键盘（打开页面就接管了，点画面会重新拿回焦点）。手机/平板：默认**不**接管，先点工具栏「键盘」，见[第 4.1 节](#41-手机平板操作触摸手势) |
| 中文输入 | 用**本机**的输入法正常打字、选字，候选框显示在本地浏览器里 |
| 粘贴到远程 | `Ctrl+V`，或点工具栏「粘贴文本」按钮（把**本机**剪贴板送到远程） |
| 从远程复制 | 在远程按 `Ctrl+C` / `Ctrl+X`，或点工具栏「获取远程文本」按钮（把**远程**剪贴板取回本机） |
| 全屏 | 工具栏「全屏」按钮，或 `F11` |
| 听到远程的声音 | 点工具栏「开启声音」，按钮变成「静音」；再点一次关掉。**默认关闭**，详见下 |
| 手机/平板操作 | 工具栏出现「鼠标 / 触屏」二选一，以及「键盘」开关；手势见[第 4.1 节](#41-手机平板操作触摸手势) |
| 断开重连 | 自动。断线后按 500ms → 10s 指数退避自动重连，切回标签页时立即重试 |

**声音为什么要点一下才响。** 这是浏览器的自动播放策略，不是设计偏好：没有用户手势，
浏览器不允许任何网页出声，`AudioContext` 会一直停在挂起状态。所以「点一下」是**机制的一部分**，
没法用配置绕开。点下去之后音频连接才建立，服务端也才开始采集——在这之前，声音这块的
服务端开销是零。

**画面下方状态条**显示：连接状态、远程分辨率、实际接收帧率、往返延迟、实测码率、声音状态。
画面静止时帧率位置会显示「静止」（此时不会有帧到达，继续显示帧率数字会看着像卡死）；
被码率控制降级时，会额外用琥珀色标出当前生效的「质量% / 帧率」。

声音这一格与「静止」同构：关闭时显示琥珀色的「无声」，开着但远程没在放声音时显示「声音 待机」
（服务端此时是停发的），真的在响才显示码率（如「声音 1.4 Mbps」）。

### 4.1 手机/平板操作（触摸手势）

设备报告有触摸屏时（`navigator.maxTouchPoints > 0`），工具栏会出现一组「鼠标 / 触屏」
二选一按钮，默认选中**触屏**（触屏设备几乎都是用手指在操作）。选择记在本机
（`localStorage`），下次打开还是它。没有触摸屏的设备不显示这组按钮——它对鼠标没有任何作用。

两种模式的差别只有一条：**手指的位置是不是指针的位置**。

| | 触屏模式 | 鼠标模式 |
| --- | --- | --- |
| 轻点 | 手指点在哪里，就在哪里点击 | 在**指针当前所在处**点击 |
| 滑动 | 不移动指针 | 指针朝与手指**相同**的方向移动（像笔记本触控板） |
| 拖动 | 指针跟着手指走 | 指针跟着手指的位移走 |

手势本身两种模式通用：

| 手势 | 效果 |
| --- | --- |
| 轻点 | 左键单击 |
| 按住不动 500ms | 右键单击（本次手势到此为止，松手不会再点一下） |
| 点一下 → 松开 → 再按住 | 按住左键，接下来移动就是拖拽。按住 200ms 后生效；期间手指移动则立即生效 |
| 快速点两下 | 双击 |
| 双指上下滑 | 滚动，方向与手机一致（双指上滑 = 页面向下走） |
| 双指左右滑 | 横向滚动 |

几点说明：

- **物理鼠标不受模式影响。** 平板接了蓝牙鼠标时，指针始终是绝对定位——把真鼠标改成
  相对移动只会让人以为鼠标坏了。模式只作用于触摸和手写笔（`pointerType` 为
  `touch` / `pen`）。
- **长按不会弹出系统菜单。** 画面上已关掉 `-webkit-touch-callout` 和文本选中，
  否则 iOS 会弹出自己的选择气泡，右键就发不出去了。
- **切后台会自动松开按键。** 手指在拖动中途切走（切标签页、来电、失焦），
  远程会收到 `mouseup`，不会一直卡在按住状态。
- **已知取舍：拖拽前面会多出一次单击。** 第一下点按是立即生效的，这样普通单击
  没有任何等待感；代价是「点一下再按住」这个拖拽手势，第一下会先真的点一次。
  用「延迟 250ms 判断是单击还是拖拽」可以去掉这次多余点击，但会让每一次普通点击
  都慢 250ms——手机上那太明显了，不划算。
- **鼠标模式下看不到指针在哪。** 远程画面本身不合成光标
  （见[第 11 节](#11-已知限制与后续计划)），所以相对模式没有位置反馈，只能靠画面上的
  悬停高亮判断指针到了哪里。触屏模式没有这个问题。
- **没有捏合缩放。** 画面本来就自适应铺满窗口，没有可缩放的目标。

#### 软键盘开关

手机 / 平板上默认**不**弹软键盘：手指点画面只操作远程。要打字时点工具栏的「键盘」（按钮变成「收起键盘」），
再点一次收起。选择记在本机，下次打开沿用。

**为什么默认关。** 远程键盘靠画面上一块透明的 `<input>` 承接——输入法必须挂在它上面才能工作
（[第 6 节](#6-中文输入是怎么实现的)）。而在手机上，**聚焦一个输入框正是弹出软键盘的充要条件**，
所以「点画面就操作」和「点画面就弹键盘」在实现上是同一件事，只能二选一。默认选前者：
挡住半个屏幕的键盘是每次点按都要付的代价，而打字是偶尔才做的事。

**怎么判断"是不是触屏设备"。** 不看 UA，也不看 `(pointer: coarse)`——这两个在 iPad 上都会骗人：
iPadOS 从 13 起默认请求桌面版网站，UA 直接写成 `Macintosh`，**和真 Mac 一模一样**；而 `pointer`
只描述"主指针"，iPad 插上妙控键盘/触控板后可能报成 `fine`，于是默认值算反、键盘照弹。
可靠的是 `navigator.maxTouchPoints`：**Mac 报 0、iPad 报 5**，且不受外接设备影响。所以判据是
"没有触点 = 真桌面；有触点且 UA 是 Mac = iPad"。

**关掉不等于不能打字。**

| | 键盘关（默认） | 键盘开 |
| --- | --- | --- |
| 手指点画面 | 只操作远程，不弹键盘 | 操作远程，键盘保持打开（点画面不会收起它） |
| 蓝牙 / 物理键盘 | **照常可用** | 照常可用 |
| 本机输入法（中文） | 不可用——需要先打开键盘 | 可用 |
| 键盘候选条上的「粘贴」 | 不可用 | 可用 |

物理键盘为什么不受影响：键盘事件是挂在 `window` 上的，判据是「目标不是表单控件」，
所以焦点在页面上（而不是在那块 `<input>` 上）时按键**照样转发**。真正需要那个焦点的只有
**输入法组合**和**键盘候选条上的粘贴**，这正是这个开关的边界。

> 键盘关着时想在手机上粘贴：用工具栏的「粘贴文本」按钮（它走剪贴板 API，不依赖键盘），
> 见[第 6.3 节](#63-粘贴ctrlv把本机剪贴板送到远程)。

### 快捷键说明

绝大多数按键会原样转发到远程（包括 `Ctrl+C`、`Ctrl+Z`、`Alt+F4` 等组合键）。

**两个组合键有额外副作用**（细节见[第 6.3、6.4 节](#63-粘贴ctrlv把本机剪贴板送到远程)）：

- `Ctrl+V`：先把本机剪贴板的文本推到远程剪贴板，再在远程按下真正的 `Ctrl+V`。
- `Ctrl+C` / `Ctrl+X`：按键照常转发（远程应用正常复制），**松开按键时**还会把远程剪贴板取回本机。

以下按键**保留给本机浏览器**，不会转发：`F5`（刷新）、`F11`（全屏）、`F12`（开发者工具）。这样即使远程画面卡住，也总能刷新页面自救。

`Alt+Tab`、`Ctrl+Alt+Del`、`Win` 键这类被本地操作系统在更底层截获的组合键**无法转发**到远程——这是 Windows 的限制，不是程序缺陷。需要时可以先用远程桌面里的其他方式（如任务栏）切换窗口。

## 5. 安全须知（务必阅读）

> ### ⚠️ 不要把本程序直接暴露到公网
>
> 本程序的设计目标是**内网 / VPN 内的临时远程协助**。它提供的能力等同于把这台电脑的鼠标键盘交给对方，一旦被陌生人连上，对方可以完全控制你的电脑（包括打开命令行、转账、读取文件）。
>
> **推荐用法**：只在内网使用，或先连上 VPN 再访问；需要跨公网时，请放在 nginx / Caddy 等反向代理后面，由代理负责 HTTPS。
>
> **IPv6 用户请特别注意：** 如果你的网络有公网 IPv6（运营商直接分配的全局地址），这台机器很可能
> **没有 NAT 保护**，从外网就能直接连到本服务。IPv4 时代「内网地址外网访问不到」的经验在这里不适用。
> 启动横幅检测到公网 IPv6 时会额外提醒；不确定的话，用 `-addr` 限制监听范围，或在路由器上关闭 IPv6 入站。

已经内置的保护：

- **口令门禁**：WebSocket 连接必须携带有效凭据，否则握手阶段直接返回 `401`，不会建立连接
- **短时效会话令牌**：登录后颁发一个 12 小时有效的随机令牌（32 字节），后续连接用令牌而不是反复传口令
- **登录失败锁定**：同一来源连续 5 次口令错误，锁定 30 秒，缓解暴力破解。IPv6 按 **/64 前缀**计数而不是单个地址——否则攻击者猜 5 次就换个地址接着猜，锁定形同虚设（一个 /64 里有 2⁶⁴ 个地址）。副作用是同一个 /64 下的设备会共享锁定状态，这在家庭/办公网里正好是想要的效果
- **恒定时间比较**：口令比对先做 SHA-256 再定长比较，避免通过响应时间推测口令
- **令牌不进日志**：令牌通过 URL 查询参数传递，日志只记录路径，不记录查询串
- **只读广播（`-view-only`）**：需要「只给别人看、不让人碰」时用它。输入在**服务端**被丢弃，改前端或直接用脚本连 WebSocket 发帧都绕不过。详见[第 5.4 节](#54-直播模式只读广播)

使用建议：

1. **始终设置口令**（`-password`），不要依赖随机口令后忘了它
2. 只在可信网络内监听；不需要外部访问时用 `-addr 127.0.0.1:8339`
3. 用完就 `Ctrl+C` 关掉程序
4. 不要把这个端口通过路由器端口映射到公网；有公网 IPv6 时，还要确认路由器**没有**放行入站连接

### 5.1 直接启用 HTTPS（`wss://`）

不配置证书时服务端只提供明文 HTTP（默认行为，见上）。**证书和私钥都给出**时改用 TLS：

```powershell
.\webvnc.exe -tls-cert _.example.com.pem -tls-key _.example.com.key
```

启动横幅的 URL 会随之全部变成 `https://`，前端会自动按页面协议选择 `ws://` 或 `wss://`，无需任何配置。
两个参数必须**成对**给出：只给一个会直接启动失败，而不是悄悄退回明文——那正好是设置这个参数想要避免的事。

**证书覆盖的域名必须和地址栏里输入的一致。** 这是唯一需要注意的坑：给 `*.example.com` 的证书
并不覆盖 `192.168.1.100`，也不覆盖 `localhost`。用后两者打开会看到浏览器的证书警告，而不是连不上。
所以启用 TLS 后请**用域名访问**：

```
https://w.example.com:8339
```

横幅会打印证书覆盖的名字和到期日期；如果一个都没覆盖到本次监听地址，还会额外给一行提示并举例
（因为这个失败长得像「服务坏了」，而不是「换个地址」）。域名要能解析到这台机器：局域网内可以在
路由器 / 内网 DNS 上把这个名字指到本机地址，或者干脆在 hosts 文件里写死。

> **证书和私钥都是机密。** 私钥（`-tls-key` 那个文件）等同于这台服务器的身份，不要提交到代码仓库、
> 不要随程序一起打包分发、不要放在共享目录里。证书过期后替换文件重启即可，没有缓存。

> **TLS 只保护传输过程，不改变访问控制。** 加了口令门禁依然是唯一的鉴权手段——证书让同一网络里的
> 其他人无法窃听口令和画面，但不能阻止别人拿着浏览器来试口令。配合公网域名使用时这一点尤其重要：
> 域名是公开的、地址是公开的，唯一挡住陌生人的就是口令强度。

### 5.2 用反向代理终止 TLS

也可以仍然用 nginx / Caddy 反向代理来终止 TLS，让后端保持明文 HTTP：

```
vnc.example.com {
    reverse_proxy 127.0.0.1:8339
}
```

Caddy 会自动申请证书并代理 WebSocket 升级。这种部署下后端建议监听回环地址
（`-addr 127.0.0.1:8339`），免得代理之外的路径也能绕过来。

### 5.3 明文 http 下拿回剪贴板：把访问地址变成 `localhost`

上一节和 §5.1 讲的是**加密**。这里讲的是另一个只在明文 http 下出现的问题——
**浏览器的剪贴板 API 在非安全上下文里根本不存在**，它和加密本身无关。

**症状**：在 `http://192.168.1.100:8339` 下按 `Ctrl+C` 复制远程文本，状态条提示剪贴板不可用；
工具栏的「粘贴文本」按钮同样无效。

**原因**：`navigator.clipboard` 只在**安全上下文**里存在，而安全上下文看的是**页面地址**：
`https://…`、`http://localhost`、`http://127.0.0.1`、`http://[::1]` 都算安全，
`http://192.168.1.100` 和公网 IPv6 地址都不算。**这不是权限问题，授予权限也没用**——
API 对象压根不存在，没有可以请求的东西（代码里同样的说明见 `RemoteScreen.vue:1039`）。

方向要分清（详见 §6.3 / §6.4）：

| 操作 | 明文 http 下 | 原因 |
| --- | --- | --- |
| `Ctrl+V` 把本机文本粘贴到远程 | ✅ 可用 | 走 `paste` 事件，文本由浏览器直接交给页面，不需要 API |
| `Ctrl+C` 把远程文本复制回本机 | ❌ 不可用 | 需要 `navigator.clipboard.writeText()` |
| 工具栏「粘贴文本」按钮 | ❌ 不可用 | 需要 `navigator.clipboard.readText()`——改用自己按 `Ctrl+V` |

所以坏掉的只有**复制回本机**这一半，而且它正好是没法用手动步骤绕开的那一半：
粘贴还能自己按键，往本机剪贴板里写没有任何替代入口。

**解法：让地址栏里是 `localhost`。** 不用碰证书，两种办法。

#### 办法一：SSH 端口转发（最省事）

```bash
ssh -L 8339:192.168.1.100:8339 用户@192.168.1.100
# 浏览器打开 http://localhost:8339
```

被控机需要开着 SSH 服务。**顺带把「本机 → 被控机」这一段也加密了**，比明文直连更安全。

#### 办法二：nginx 四层转发

本机装了 nginx 的话，`stream` 模块（四层 TCP 透传）就够：

```nginx
# stream {} 必须和 http {} 平级，不能写进 http {} 里
stream {
    server {
        listen 8339;
        proxy_pass 192.168.1.100:8339;   # 四层里不写 http://，也不写 ws://
    }
}
```

**为什么 `stream` 比 `http` 省事**：四层不解析 HTTP，WebSocket 的 `Upgrade` 头原样透传，
不需要任何额外配置。用 `http {}` 也能成，但要多三行：

```nginx
http {
    server {
        listen 8339;
        location / {
            proxy_pass http://192.168.1.100:8339;   # 这里必须带 http://,且末尾不加 /
            proxy_http_version 1.1;
            proxy_set_header Upgrade    $http_upgrade;
            proxy_set_header Connection "upgrade";
        }
    }
}
```

少了中间两行 WebSocket 会握手失败——**页面能打开、登录也能过，但画面永远是黑的**。
另外两个模块的 `proxy_pass` 语法正好相反（`stream` 里**不能**写 `http://`），这点容易记混。

nginx 默认编译可能不含 stream：

```bash
nginx -V 2>&1 | tr ' ' '\n' | grep stream
```

看到 `--with-stream` 才算有；只给出 `--with-stream=dynamic` 时要装 `libnginx-mod-stream`，
或手动加一行 `load_module modules/ngx_stream_module.so;`。改完 `nginx -t` 验证再 `nginx -s reload`。

#### 三个副作用

1. **客户端 IP 会被折叠成 `127.0.0.1`。** 登录失败锁定按来源 IP 计数（`server/auth.go:117`
   的 `lockoutKey`），取的是 TCP 连接对端的地址（`r.RemoteAddr`）。走代理后所有请求都从本机
   进来，服务端分不清是谁在试——**别人猜错口令会把你一起锁掉**（§5 那条「5 次错误锁 30 秒」）。
   webVNC **不读** `X-Forwarded-For` / `X-Real-IP`，所以有意识地加上这两个头也没用；
   四层的 `proxy_protocol` 同样没用，服务端不解析 PROXY 协议。自己用无所谓，别拿它当多人入口。
2. **只对你本机的浏览器有效。** `localhost` 绑在每个设备自己身上——手机访问
   `http://192.168.1.100:8339` 依旧拿不到剪贴板 API。要覆盖所有设备，正路是 §5.1 的
   `-tls-cert` / `-tls-key`，或用 §5.2 的反代提供一个带真实证书的域名。
3. **超时不用调。** 服务端每 25 秒发一次 WebSocket ping（`server/ws.go:21` 的 `pingPeriod`），
   连接上一直有流量：nginx 默认 `proxy_read_timeout 60s`、`stream` 默认 `proxy_timeout 10m`，都够。

### 5.4 直播模式（只读广播）

想把自己的桌面推给别人看，但**不希望对方能碰到这台电脑**时，加 `-view-only`：

```bash
./webvnc -view-only -password 演示口令          # Linux
.\webvnc.exe -view-only -password 演示口令      # Windows
```

此时连上来的每个客户端都只能看画面、听声音。启动横幅会写一行 `客户端权限 只读`。

**开关在服务端，客户端解不开。** 这一点是刻意的，也是它和「工具栏上放个只读开关」的区别：
工具栏上的开关谁都能点，那只是「我自己不看操作」，不是限制。`-view-only` 下：

- 前端**不显示**「鼠标/触屏」「键盘」「粘贴文本」「获取远程文本」，改为一个不可点的「直播模式 · 只能观看」标签，
  画面上还有一个常驻徽标；点画面**不会弹软键盘**（观众没有要输入的东西）
- 但**真正把关的不在前端**：服务端收到任何输入帧直接丢弃（`server/ws.go` 的 `Client.handle`）。
  所以就算有人改前端、或者拿脚本直接连 WebSocket 发帧，也照样动不了这台电脑

拦截用的是**白名单**而不是黑名单：只放行 `ping`（客户端靠它探测连接），其余一律丢弃。
这样将来新增一种输入消息时，默认是被拦住的，而不是默认放行——漏了的后果是失效，不是泄漏。

几个边界：

- **剪贴板一并拦下。** 「粘贴文本」（把本机文本写到远程并粘贴）和「获取远程文本」（把远程剪贴板取到本机）
  在只读时都不可用。后者尤其重要：能把对方机器的剪贴板内容取走，那已经不是「看屏幕」了
- **多个观众可以同时看**，`-max-clients` 照常生效
- **声音是独立的**，只读不影响 `/ws/audio`，观众照常能听
- **旧缓存页面**不认识这个标记，界面看上去照旧可点，但服务端照样丢——退化成「点了没反应」，不会泄漏控制

## 6. 中文输入是怎么实现的

这是本项目里最需要专门设计的一块，方案和原因如下。

### 6.1 问题所在

如果像转发英文字母那样，把拼音按键一个个转发到远程再让远程输入法处理，会出现：远程弹出了候选框，但**你本地浏览器看不到候选词，也没法选字**——因为候选框在远程那台机器的屏幕上（而且候选框属于输入法窗口，往往还截不到画面里）。体验完全不可用。

### 6.2 采用的方案：本地输入法合成 + 整句注入

关键在于把"选字"这一步留在**浏览器本地**完成：

```
用户在本机输入法里打 "nihao" → 候选框显示在本地浏览器（本机输入法负责）
        ↓ 用户选字
compositionend 事件，e.data === "你好"
        ↓ 整段字符串通过 WebSocket 上行
{ "type": "text_input", "text": "你好" }
        ↓ 服务端不再模拟按键，而是用 Unicode 注入
SendInput(KEYEVENTF_UNICODE)，逐字符写入当前焦点窗口
```

实现要点：

- 画面上覆盖了一个**透明但真实存在**的 `<input>`（`opacity: 0`，不是 `display:none`，否则输入法不会挂载），输入法挂在它上面。**它是否持有焦点由一个开关决定**：桌面端常驻，手机/平板上默认不聚焦（聚焦就会弹软键盘），见[第 4.1 节](#41-手机平板操作触摸手势)。关掉开关时它还带 `inputmode="none"`，作为「焦点从别处飘过来也不会弹键盘」的兜底
- 用浏览器原生的 `compositionstart` / `compositionupdate` / `compositionend` 事件，输入法、候选框、选字全部在本地正常进行
- **只在 `compositionend` 时**把最终确定的整段文字发过去，走独立的 `text_input` 通道
- **组合过程中的按键一律不转发**（判断 `e.isComposing` 或 `keyCode === 229`），否则会和输入法打架
- 服务端用 `KEYEVENTF_UNICODE` 直接写入字符码点，**绕开远程的键盘布局和输入法**，所以远程无论是什么输入法状态都能正确落字

英文、数字、方向键、快捷键（`Ctrl+C` 等）走原来的单键通道，两个通道并存互不干扰。

### 6.3 粘贴（`Ctrl+V`：把本机剪贴板送到远程）

`Ctrl+V` 被单独拦截，但**不是**把文字逐字打进远程，而是走剪贴板：

1. 读本机剪贴板（`navigator.clipboard.readText()`）；
2. 把文本通过 `clipboard_push` 推到**远程**的剪贴板；
3. 在远程**按下真正的 `Ctrl+V`**。

第 3 步是关键：远程应用执行的是它自己的粘贴逻辑，所以终端、密码框、「只粘纯文本」这类行为和在本地按 `Ctrl+V` 完全一致。（早先的版本是把文本逐字符注入，那样远程应用收到的是"有人在飞速打字"，而不是一次粘贴。）

**按键是合成的，不是转发的。** 读取剪贴板是异步的，而按键顺序不能乱：如果先转发真实的 `V` keydown/keyup，用户完全可能在等待期间松手，于是远程收到"先抬起、后按下"的 `V`。所以按下的那一刻就吞掉这组按键，等剪贴板推完再自己合成 `keydown` + `keyup`。顺序由我们决定，天然正确——远程此刻 `Ctrl` 本来就按着，合成的 `V` 正好凑成一组合法的 `Ctrl+V`。

**推剪贴板和发按键走同一条 WebSocket**，服务端按到达顺序处理，所以剪贴板一定先于按键写入，不需要额外的等待往返。

几种边界情况：

| 情况 | 行为 |
| --- | --- |
| 本机剪贴板没有文本 | 照常转发一次普通的 `Ctrl+V`（状态条：`本机剪贴板没有文本，已按普通 Ctrl+V 转发`） |
| 超过 256 KB | 本机就拦下不发（状态条：`剪贴板内容过大（上限 256 KB），未发送`） |
| 远程剪贴板写入失败 | 状态条：`远程剪贴板写入失败：…（远程可能粘贴了旧内容）`——这条提示很重要，因为**此时远程会粘出它自己原有的剪贴板内容**，是唯一能发现"粘错了"的线索 |
| 成功 | 状态条：`已粘贴 N 个字符` |

> 覆盖远程剪贴板是这个方案的固有代价，不能避免——要让远程应用执行"自己的"粘贴，就只能走它自己的剪贴板。它和[第 6.4 节](#64-复制ctrlc把远程剪贴板取回本机)的取回合起来，效果是一份**两边共享的剪贴板**。

工具栏的「粘贴文本」按钮做的是同一件事，供不便按键盘时使用。

> ⚠️ **安全上下文决定了走哪条路。** 浏览器只在 **https、`localhost`、`127.0.0.1`** 三种情况下提供 `navigator.clipboard`。用局域网 IP 或 IPv6 地址以**明文 http** 打开页面时（例如 `http://192.168.1.100:8339`、`http://[2001:db8:...]:8339`），这个接口**根本不存在**：不会有权限弹窗，也没有任何设置能打开它。这是浏览器的安全模型，不是本程序的限制。
>
> **服务端和浏览器在同一台机器上时（很常见），把地址换成 `http://localhost:8339` 就直接解决**——`localhost` 算安全上下文，局域网 IP 不算。点按钮时会直接提示这个 URL。
>
> 从**别的设备**访问时没有 localhost 可用，那就**配上证书走 https**（`-tls-cert` / `-tls-key`，见[第 5.1 节](#51-直接启用-httpswss)）：安全上下文是按地址判定的，https 下任何地址都算。
>
> **没有安全上下文时 `Ctrl+V` 仍然可用**，只是换了条路：退回监听浏览器的 `paste` 事件，从事件本身拿到文本（事件携带文本，不受这条限制），再走同样的「推剪贴板 + 合成 Ctrl+V」。这条路不需要任何权限，但**依赖浏览器把事件发出来**——这正是它不能当主路径的原因：`paste` 事件什么时候发、发给哪个元素由浏览器决定，**不发时一声不响、和功能坏了完全一样**。
>
> 所以：**状态条上出现「已粘贴 N 个字符」才算成功**。什么都没显示就是本机这边就没发出去。
>
> 「获取远程文本」（下一节）在明文 http 下**只能给出提示**，因为它需要的是写入接口，而写入没有事件可以兜底。此时状态条会说 `浏览器不在此地址提供剪贴板写入，改用 https 或 http://localhost…`——两条路怎么走见[第 5.3 节](#53-明文-http-下拿回剪贴板把访问地址变成-localhost)。

### 6.4 复制（`Ctrl+C`：把远程剪贴板取回本机）

在远程按 `Ctrl+C` 时：

1. 按键**照常转发**，远程应用正常执行复制；
2. **松开 `C` 的时候**，客户端发 `clipboard_pull` 把远程剪贴板取回来；
3. 用 `navigator.clipboard.writeText()` 写进本机剪贴板（状态条：`已复制 N 个字符到本机`）。

`Ctrl+X`（剪切）同样处理。

**为什么在松开时拉取，而不是按下时。** `SendInput` 只是把输入排进目标线程的队列，应用是**稍后**才处理 keydown 并写入剪贴板的。如果在按下时立刻拉取，很可能赶在应用复制之前，拿回旧内容。Windows 的输入队列是先进先出的，同一个线程一定先处理完 keydown 再处理 keyup——**keyup 到达时，复制必然已经完成**。

**为什么记标志位而不是看 `e.ctrlKey`。** 有人习惯先松 `Ctrl` 再松 `C`，那时 `C` 的 keyup 里 `ctrlKey` 已经是 false，只看它就会漏掉这次复制。所以在 keydown 时记一个标志，keyup 时凭标志判断。

**远程用右键菜单复制怎么办？** 那时没有 `Ctrl+C` 可以拦截，客户端根本不知道发生了复制。用工具栏的「获取远程文本」按钮手动拉一次——它调用的是同一段逻辑。

> 只支持**文本**。远程剪贴板里是图片或文件时，状态条会显示 `远程剪贴板里没有文本`（而不是报错或静默）。图片、文件、HTML 等格式不在本版本范围内。

> 明文 http 下写入接口不可用，状态条会提示一次（**每个会话只提示一次**，否则每次 `Ctrl+C` 都刷屏）。读取不受影响，只是取回来放不进本机剪贴板。

### 6.5 一个容易踩的坑

覆盖层那个 `<input>` 会同时触发 `keydown` 和 `input` 事件。如果两个都转发，每敲一个字符都会在远程打出两个（`"aa"`）。所以 `input` 事件**只负责清空缓冲区，绝不转发**——物理按键走 `keydown`，合成文字走 `compositionend`，粘贴走 `paste`，三者各司其职。

## 7. 工作原理

```
┌─────────────────────────┐   WebSocket /ws  (画面，双向复用)   ┌──────────────────────────┐
│      浏览器 (Vue3)       │ <────────────────────────────────> │     Go 后端 (Windows)     │
│                          │  下行: 二进制帧 (H.264 / JPEG)      │  GDI BitBlt 抓屏          │
│  <canvas> 绘制帧          │  上行: JSON 指令                    │  Media Foundation 编码    │
│  WebCodecs / 位图解码     │ ─────────────────────────────────> │  SendInput 注入           │
│  透明 <input> 接管键盘    │                                    │                          │
│  鼠标/键盘/输入法事件      │  WebSocket /ws/audio  (声音，只下行) │  WASAPI 回环采集          │
│  AudioContext 播放 PCM   │ <───────────────────────────────── │  PCM → 16-bit 转换        │
└─────────────────────────┘  下行: 二进制 16-bit PCM            └──────────────────────────┘
```

**抓屏（`server/capture_windows.go`）**

每帧执行 `GetDC(NULL)` → `BitBlt`/`StretchBlt` 拷进内存 DC 的 **DIB section** → 原地交换 R/B 通道并补上不透明的 alpha → **画面有变化才** `image/jpeg` 编码并广播给所有客户端。内存 DC 和 DIB section 按分辨率复用，只有分辨率变化时才重建。

用 DIB section 而不是「`CreateCompatibleBitmap` 画完再 `GetDIBits` 读回」是有原因的：`GetDIBits` 要求那张位图**没有被选进任何 DC**，而池化的内存 DC 做不到这点，部分显示驱动会直接返回 0（`ERROR_INVALID_PARAMETER`），表现为只有一部分机器上抓屏全黑、日志里一行 `GetDIBits failed`。DIB section 让 GDI 直接把像素画进可读缓冲区，没有这条规则要遵守，顺带省掉每帧一次整屏拷贝。

把 alpha 强制写成 `0xFF` 是**必须**的：未定义或复用的 alpha 字节会让静止画面的像素每帧都不相等，静止检测就永远不会命中。

### 帧间压缩（H.264）

默认走**帧间**：每帧只编码与前一帧的差异，而不是各自独立成一张图。同一段桌面素材上实测
（1366×768，同一编码器），关键帧约 6.9 KB、差值帧约 1.6 KB；换成低延迟 VBR 后关键帧约 4.7 KB、
差值帧约 450 B，整段画面约 65 kbps。差值帧之所以是省带宽的地方，就在于它只需要描述变化的那一块像素。
编码器是 **Windows 自带的 Media Foundation H.264 编码器 MFT**，不引入 cgo、不附带外部 exe，
单个二进制文件的形态不变。

帧内 JPEG 没有被删掉，它是**回退方案**，也是 `-codec jpeg` 时的唯一路径。完整的两条路：

| 模式 | 行为 |
| --- | --- |
| `auto`（默认） | 启动时探测本机有无 H.264 编码器：有就用帧间，没有就整个退回帧内并在启动横幅里说明原因。运行中编码器报错也会即时退回（**仅** `auto` 模式） |
| `h264` | 只用帧间。启动时探测失败就**直接启动失败**并给出原因，而不是发一块黑屏。客户端解不了 H.264 时连接会被拒绝并附带说明 |
| `jpeg` | 只用帧内，也就是这个功能之前的行为 |

**关键帧只能靠 GOP。** `ICodecAPI` 的 `CODECAPI_AVEncForceKeyFrame` 在配置阶段报告"支持"，
但每一帧实际调用都返回 `E_NOTIMPL`——无法按需强制关键帧。于是 GOP 是客户端拿到画面的**唯一**途径，
`KeyframeEvery` 默认设为 1 秒：新连上来的客户端最多等 1 秒就能解码，而不是等到某个随机的 GOP 边界。

**几个不写下来一定会踩的点**（都是实测出来的，且**都是静默失败**）：

| 细节 | 为什么 |
| --- | --- |
| `MF_LOW_LATENCY` 要同时设在 **transform 属性、输入类型、输出类型**三处 | 文档列了三处，而编码器实际读的是**输入类型**上的那个。只设输出类型时它一声不响地缓冲 12 帧——表现为画面延迟 400ms，日志里没有任何异常 |
| 驱动编码器 MFT 之前必须设 `MF_TRANSFORM_ASYNC_UNLOCK` | 在 Media Foundation 管道**之外**驱动异步 MFT 的客户端必须解掉这把锁。不设的话异步编码器会被当成同步的用，`ProcessOutput` 直接返回 `E_UNEXPECTED` |
| 异步与否要读 **transform 自己的属性存储**判断，不能猜 | `IMFTransform::GetAttributes` 取 `MF_TRANSFORM_ASYNC`；属性不存在就是同步。这个差异决定了调用方要不要自建事件循环 |
| MFT 的 COM 调用必须固定在**同一个 OS 线程**上 | COM 按线程区分。编码器跑在一条 `runtime.LockOSThread()` 的 goroutine 里，靠 channel 往返，不迁移线程 |
| 输入格式是 **NV12**，色度要做 BT.709 有限范围定点转换 | RGB→YUV 的系数和范围写错不会报错，只会让颜色整体偏，且是"看起来好像也没错"的那种偏 |
| 编码器在**设定输出类型之前**拒绝枚举输入类型 | 返回 `MF_E_TRANSFORM_TYPE_NOT_SET`（`0xC00D6D60`），顺序错了就会被误判成"这台机器没有编码器" |
| `MFTEnumEx` 的 GUID 参数**按值传递**，因此只在 amd64 上成立 | 其他架构走 `server/video_other.go`，直接报告没有编码器 |

> Intel QSV 那两个编码器在本机测下来**用不了**：即便解掉 `MF_TRANSFORM_ASYNC_UNLOCK`，它们仍然
> 报告自己是异步的，构建会话时 `ProcessOutput` 返回 `0x8000FFFF`。它们需要一个完整的 MF 事件循环，
> 而微软自带的那个编码器现在能稳定做到零帧缓冲，所以没有理由再写那套循环。探针会把它们如实列出来。

**帧间模式下码率控制的 `quality` 旋钮是空转的。** H.264 编码器不接受 JPEG 质量参数（它有自己的
码率控制），所以超预算时控制器只能压帧率，`已限速` 那行也就只显示帧率、不再显示一个变了也没用的
质量百分比。真正起作用的是 `-max-bitrate`。

**输入注入（`server/input_windows.go`）**

- 鼠标移动用 `MOUSEEVENTF_ABSOLUTE`，把像素坐标按 `0..65535` 归一化到主显示器
- 按键用虚拟键码（浏览器 `KeyboardEvent.code` → Windows VK 的映射表在 `server/input.go`），方向键、小键盘除号、右侧 Ctrl/Alt 等会带上 `KEYEVENTF_EXTENDEDKEY`
- 输入法合成出的中文用 `KEYEVENTF_UNICODE` 逐字符注入（**只有输入法走这条路**，粘贴走剪贴板，见[第 6.3 节](#63-粘贴ctrlv把本机剪贴板送到远程)）
- 剪贴板读写（`server/clipboard_windows.go`）是纯 Win32 调用，不引入 `x/sys/windows`：读的时候用 `RtlMoveMemory`（`kernel32.dll` 导出的 `memmove`）把系统内存块拷进 Go 切片，而不是把那个句柄当 Go 指针用——把整数转回指针正是 `go vet` 会（正确地）质疑的写法

**声音采集（`server/audio_windows.go`）**

全项目唯一使用 COM 的地方，也是唯一需要手写 vtable 调用的地方。链路是
`CoInitializeEx(MTA)` → `CoCreateInstance(MMDeviceEnumerator)` → `GetDefaultAudioEndpoint(eRender, eConsole)`
→ `Activate(IAudioClient)` → `GetMixFormat` → `Initialize(SHARED, LOOPBACK)` →
`GetService(IAudioCaptureClient)` → `Start()`，之后按设备周期的**一半**轮询取包（Win11 上约 5ms）。
设备混音格式通常是 `WAVE_FORMAT_EXTENSIBLE` + float32，逐样本转成 16-bit 后再按 20ms 重新分包——
设备的回调块大小（实测约 10ms）和线上包长并不一致，不重新分包就会让线上格式跟着设备漂。

几个不写下来一定会踩的点：

| 细节 | 为什么 |
| --- | --- |
| `CoInitializeEx` 之前先 `runtime.LockOSThread()` | COM 是按**线程**初始化的，而 goroutine 会在系统线程之间迁移 |
| 用 MTA，不用 STA | STA 需要消息泵，而阻塞在 sleep 里的 goroutine 不会泵消息，会静默卡死 |
| `AUDCLNT_S_BUFFER_EMPTY`（`0x08890001`）按**成功**处理 | 它是「这一轮没数据」的正常返回。当成错误就会把常态空闲判成致命故障 |
| HRESULT 先截成 32 位再看符号 | x64 调用约定不保证 32 位返回值的高半部为零，直接和 0 比较会误判 |
| `WAVEFORMATEXTENSIBLE` 在 Go 里**平铺**声明 | C 里是 18 字节紧凑布局，Go 会把嵌套的 18 字节结构体补到 20 字节，`SubFormat` 整体后移 4 字节——读到的是垃圾，但不崩也不报错 |
| 判 SubFormat 要**完整比较 16 字节** | 只比 `Data1`（PCM=1 / float=3）是流传很广的捷径，会匹配上所有共享这 4 字节的 GUID |
| 拔设备时任何调用都可能返回 `AUDCLNT_E_DEVICE_INVALIDATED` | 不是固定在某一处。做法是释放全部接口重新 `Activate`，带 100ms → 2s 指数退避 |
| `Initialize` 失败后不原地重试 | 同一个 `IAudioClient` 上再调会返回 `AUDCLNT_E_ALREADY_INITIALIZED`，必须释放后重新获取 |

> **没有播放时，回环根本不产生数据包**——不是全零包，也不是带 SILENT 标志的包，而是
> `GetNextPacketSize` 一直返回 0。这个「没有数据」本身就是最准确的静音信号，比逐样本看振幅可靠得多，
> 所以静音检测主要靠一个数据缺口看门狗，全零包检查只作为兜底（对付明明不出声却保持流打开的应用）。

**几个关键实现细节**

| 细节 | 为什么 |
| --- | --- |
| 启动时先 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` | 不设置的话，在缩放显示器上 Windows 会返回虚拟化的分辨率，截图模糊且鼠标点偏 |
| 抓屏用 `CreateDIBSection` 而不是 `GetDIBits` 读回 | `GetDIBits` 要求位图未被选进 DC，违反时**多数驱动容忍、少数直接返回 0**——正是「只有部分电脑报错」那种 bug 的形状 |
| 启动时 `SetConsoleOutputCP(65001)` | 中文系统控制台默认 GBK 代码页，不改的话启动横幅和日志全是乱码 |
| 没有客户端时跳过抓屏和编码；没有音频客户端时连采集设备都不打开 | 空闲时 CPU 占用接近 0 |
| 声音走**独立**的 `/ws/audio` 连接，不与画面共用 | WebSocket 没有优先级，一个 200KB 的 JPEG 在慢链路上要发 200ms，20ms 的音频包排在它后面就是一次断音 |
| 音频入队队列 16 槽（画面是 4） | 约 320ms 缓冲。策略仍是「塞满丢新包、绝不阻塞」，但音频丢包的代价比丢一帧画面高 |
| 浏览器按**实测到达帧率**回放，而不是按标称采样率 | 端到端实测只有真实时间的 99.42%（采集设备本身是 99.94%）。按 100% 回放会在约 20 秒内耗尽 100ms 抖动余量，之后每个包一到就播、再无余量可失 |
| 音频包每次广播都**新建**缓冲区，不回收复用 | 与画面路径相反：这个包在 `broadcastAudio` 返回后仍被各客户端的发送队列持有，回收会当场改掉排队中的数据 |
| 传输层（单写者纪律、ping/pong、写超时、入队丢弃）抽成 `wsConn`，画面与声音共用 | 那套纪律是整个传输层最微妙的地方，抄成两份迟早漂移 |
| 扣减音频占用时用**标称**码率而不是实测值 | PCM 码率恒定，没有可测量的波动；用固定值扣可以避免控制器追着音频统计抖动来回调 |
| 像素与上一**已发送**帧逐字节比较，一致就跳过编码和发送 | 静止桌面带宽为 0；比较首字节不同即短路，运动画面几乎无额外开销 |
| 码率控制器降级后清空静止检测的基准帧 | 否则静止画面会一直停留在降级前那张糊图上——恰好是用户正在看它的时候 |
| 码率控制器按「实际入队的字节数」统计，丢帧不计入 | 统计产出会让它对已经被队列丢弃吸收的拥塞继续降级 |
| 抓屏定时器在每次 tick 的**开头**重设，而不是结尾 | 编码耗时否则会叠加到每个周期上，把帧率悄悄拉低 |
| 客户端发送队列满了就丢帧，不阻塞 | 一个慢客户端不该拖垮所有人的画面 |
| 只允许 writePump 一个 goroutine 写 socket | gorilla/websocket 不允许并发写，`ping` 的回复也走发送队列 |
| 失败锁定前先把地址归并：IPv4-mapped（`::ffff:a.b.c.d`）还原成 IPv4，IPv6 收敛到 /64 | 双栈监听下同一台 IPv4 主机会以两种形式到达；而按单个 IPv6 地址计数等于没锁——换个地址就能继续猜 |

## 8. 通信协议

画面走 `/ws?token=<令牌>`，声音走 `/ws/audio?token=<令牌>`，两条**独立**的连接，鉴权方式相同。

### 画面下行（服务端 → 浏览器）

| 类型 | 内容 |
| --- | --- |
| **二进制帧** | 2 字节帧头 + 编码后负载。见下方「帧格式」 |
| **文本帧** | JSON 控制消息 |

#### 帧格式

每个二进制帧的头两个字节是：

| 偏移 | 含义 |
| --- | --- |
| `[0]` | 编解码器：`0` = JPEG，`1` = H.264 |
| `[1]` | 标志位，bit0 = **关键帧**（解码器可以从此帧开始解码） |

后面的负载按 `[0]` 解释：

- **`0` JPEG** —— 一张完整的 baseline JPEG，每一帧都能独立解码。浏览器 `createImageBitmap` 直接解。
- **`1` H.264** —— 一个 Annex B 格式的访问单元，**带起始码，SPS/PPS 在每个关键帧前重复内嵌**。
  参数集在带内（而不是带外另发）是刻意的：WebCodecs 解码 Annex B 流时**不需要** `description`，
  于是既不用构造 avcC box，也没有一份初始化数据要跟编码器保持同步。

> **编解码器逐帧标注，而不是连接时约定一次。** 服务端会在中途换用编码器（客户端解不了 H.264 时整个
> 流会切回 JPEG），如果客户端靠"连接时被告知过什么"来解码，那么每次切换后都会拿错误的解码器去解
> 下一帧。逐帧标注让切换对客户端来说是自动的。
>
> **JPEG 负载前面也因此多了 2 个字节。** 帧内压缩本身没有任何改动，但这条连接上的所有二进制帧
> 现在都带帧头，不再是从第 0 字节开始的裸 JPEG。

#### 能力协商

连接 URL 上有两个参数，都是**必须**的：`fmt` 声明页面认识哪种帧布局，`v` 声明客户端能解什么。

| URL | 含义 |
| --- | --- |
| `/ws?token=…&fmt=1` | 页面按当前的**带帧头**布局解析二进制帧。当前前端的固定值 |
| `/ws?token=…&fmt=1&v=h264` | 同上，并且客户端能解码 H.264。只在 `VideoDecoder` 存在时才发送——它需要**安全上下文**，所以同一个浏览器在 `https` 下会声明、在明文 `http` 下不会 |
| `/ws?token=…`（不带 `fmt`，或不等于 `1`） | 页面是**旧版本**（见下），连接被**拒绝**，关闭帧的 reason 里写明原因 |
| `/ws?token=…&fmt=1`（不带 `v`） | 客户端不能解码 H.264。服务端会把整个流切到帧内 JPEG，**之后不再切回** |

`-codec h264` 时，不带 `v=h264` 的连接会被**拒绝**，关闭帧的 reason 里写明原因（这是握手失败时唯一
能传到页面上的一句话，所以它必须自解释）。reason 有 **123 字节**的硬上限，超过整个关闭帧作废、
用户什么也看不到——中文一个字 3 字节，很容易超。两条拒绝消息都有测试盯着这个上限。

> **为什么要有 `fmt`。** 前端是嵌进二进制里的，正常情况下两边永远同源，够不到版本不一致。唯一的
> 来路是**只重编了一半**——`go build`，或者 `build.ps1 -SkipFrontend`，而 `frontend/dist` 还是旧的。
> 这种组合的症状是所有症状里最糟的一种：旧页面把整个带帧头的消息当成裸 JPEG 交给
> `createImageBitmap`，它拒绝，而这个拒绝被同一个「跳过损坏帧」的 catch 吞掉，于是**黑屏、带宽图
> 还在动、两边控制台都没有任何输出**。所以这里不做「兼容旧格式」，直接拒绝并说清楚原因：旧页面同时
> 也完全没有 H.264 那条路径，真喂给它只会换来更难查的怪状态。
>
> **遇到「黑屏但带宽在动」，先看这句 reason。** 如果它出现了，重新完整构建即可（在 `frontend/` 里
> 跑 `npm run build`，或者跑 `build.ps1` 时**不要**带 `-SkipFrontend`）。

> **纯 HTTP 局域网下拿不到帧间压缩。** WebCodecs 需要安全上下文，明文 HTTP 页面上 `VideoDecoder`
> 不存在，于是客户端不声明能力、服务端退回 JPEG——行为和加这个功能之前**完全一致**，没有回归。
> 想要帧间压缩就得上 HTTPS（部署时传入自己的证书，如 `_.example.com.pem` / `_.example.com.key`），见[第 5.1 节](#51-直接启用-httpswss)。

控制消息：

```jsonc
// 连接建立时下发，分辨率变化时重新下发
// viewOnly 为 true 表示服务端开了 -view-only（第 5.4 节）：页面据此把界面改成只读。
// 它是**纯附加字段**，旧页面不认识就忽略，服务端照样丢弃输入，所以不涉及协议版本
{ "type": "screen", "width": 1920, "height": 1080, "viewOnly": false }

// 回应上行的 ping，t 为服务端毫秒时间戳
{ "type": "pong", "t": 1730000000000 }

// 每个统计周期（1s）下发一次，描述当前推流状态
// fps/quality 是当前**生效**值（可能已被码率控制调低），kbps 是实测出口码率
// idle 为 true 表示画面静止、当前没有帧在发
// video 是当前编码器：h264 或 jpeg，供界面显示；帧间模式下 quality 无意义（见第 7 节）
{ "type": "stats", "fps": 15, "quality": 45, "kbps": 820, "idle": false, "limited": true, "video": "h264" }

// 回应上行的 clipboard_pull / clipboard_push
// op 回显是哪一种：pull 带 text（要写进本机剪贴板），push 只报成败
// ok=false 才是真失败；ok=true 而 text 为空表示剪贴板里本来就没有文本
{ "type": "clipboard", "op": "pull", "ok": true, "text": "远程复制的文字", "error": "" }
{ "type": "clipboard", "op": "push", "ok": false, "text": "", "error": "剪贴板被其他程序占用" }
```

> 剪贴板回包**带重试**：客户端发送队列只有 4 格且满了会静默丢帧，但剪贴板回包每个用户动作只有一条，
> 丢掉和"功能坏了"无法区分。所以服务端会重试约 1 秒（20ms 一次）直到塞进队列，
> 且重试在独立 goroutine 里，不阻塞同一条连接上的鼠标键盘。

> 前端**必须**依赖 `stats` 而不是自己数帧：画面静止时一帧都不发，自己数出来的帧率会冻结在最后一个值上，看起来像卡死而不是静止。

> `screen` 里的宽高始终是**桌面真实分辨率**，与 `-scale` 无关。客户端据此把画布坐标换算成远程像素坐标，服务端拿到的一定是真实屏幕坐标。

### 画面上行（浏览器 → 服务端）

```jsonc
// 鼠标移动（坐标为远程屏幕像素）
{ "type": "mousemove", "x": 123, "y": 456 }

// 鼠标按键：button 取值 left / middle / right / back / forward
{ "type": "mousedown", "button": "left" }
{ "type": "mouseup",   "button": "left" }

// 滚轮：deltaX/deltaY 为**浏览器原始像素值**（不预先翻转符号）；服务端按 100px = 1 格
// 累积换算成 Windows 的 120 单位滚动量，不足一格的余量会留给下一次，触控板小步滚动不会丢
{ "type": "wheel", "deltaX": 0, "deltaY": -100 }

// 键盘（code 为 KeyboardEvent.code，物理键位，与本地键盘布局无关）
{ "type": "keydown", "key": "a", "code": "KeyA" }
{ "type": "keyup",   "key": "a", "code": "KeyA" }

// 输入法合成结果，整段 Unicode 直接注入（**仅用于输入法**；粘贴不走这里）
{ "type": "text_input", "text": "你好" }

// 取回远程剪贴板的文本，回包见下行的 clipboard
{ "type": "clipboard_pull" }

// 把文本写入远程剪贴板，回包见下行的 clipboard。上限 256 KB（UTF-8 字节数）
{ "type": "clipboard_push", "text": "要粘贴到远程的文字" }

// 延迟探测
{ "type": "ping" }
```

无法映射的按键会被静默忽略，不会导致连接断开。

> **`-view-only` 时上面这些上行消息几乎全部被丢弃**，只留 `ping`。判据在
> `Client.handle`（`server/ws.go`）一处，用的是白名单：不在名单上的类型默认不生效。
> 这一条是服务端强制的边界，不是前端约定——绕过页面直接发帧也一样。

> **滚轮的符号在服务端翻转，而且只翻竖直方向。** 浏览器和 Windows 对竖直滚动的正负号定义**相反**
> （浏览器 `deltaY > 0` 是向下滚，Windows 的正值却是向上滚），水平方向则**一致**（两边正值都是向右）。
> 这种"一个轴反、一个轴不反"的不对称正是最容易写错的地方——当初就是漏了竖直方向的翻转，
> 导致滚轮上下颠倒。`server/hub_test.go` 的 `TestWheelDirection` 把两个轴的方向都钉住了。

> **触摸操作不新增任何协议。** 长按右键、点按拖拽、双指滚动全都在浏览器端被识别成
> 上面已有的 `mousemove` / `mousedown` / `mouseup` / `wheel`，服务端一视同仁。双指滚动
> 送出的也是**浏览器约定**的 `wheel`（双指上滑 = 正 `deltaY`），竖直方向的翻转同样由服务端做。

### 声音（`/ws/audio`）

独立连接，**只下行**——浏览器不会往这条连接发任何东西，除了保活的 `ping`。和画面那条各有各的
生命周期，互不影响。

```jsonc
// 连接建立时下发一次，之后不再重复。格式变了只会是服务端重启，那是新连接
{ "type": "audio", "sampleRate": 44100, "channels": 2, "bits": 16, "packetMs": 20 }

// 每个统计周期（1s）下发一次
{ "type": "audioStats", "kbps": 1411, "idle": false }
```

握手之后，每条**二进制**消息就是恰好 20ms 的原始 PCM：

- 交织排列（`L R L R …`），**小端序**，有符号 16-bit；
- 长度 = `sampleRate × channels × 2 × 0.02`，44.1 kHz 立体声是 3528 字节；
- 默认播放设备安静时**不发**（`audioStats` 的 `idle` 变 `true`），恢复时立刻续传，不补发中间那段。

`bits` 目前恒为 16。前端仍然会检查它并拒绝其它取值：按错误的宽度去解读二进制只会得到噪音，
这种失败模式不如直接拒绝来得清楚。

> **没有音画同步。** 两条独立连接、没有共同时钟，浏览器只是把收到的 PCM 按自己的时钟连续排下去。
> 远程协助够用（两者本来就相差不到一帧），对口型之类的场景不够——那需要共同的时基和播放对齐，
> 是另一个量级的工作。

> **`-audio=false` 时这个端点直接返回 404。** 前端在几次失败后会停止重试（而不是在后台无限重连），
> 状态条上给出「连续 N 次连接失败，已停止重试」。

### HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/login` | 提交 `{"password":"..."}`，成功返回 `{"token":"...","expiresAt":...}`；口令错误返回 401，失败过多返回 429 |
| `GET` | `/api/verify?token=` | 校验令牌是否仍然有效，前端据此区分"口令失效"和"网络断开" |

## 10. 常见问题

**Q: `go build` 报错 `pattern all:frontend/dist: no matching files found`**

前端还没构建。先执行 `cd frontend && npm install && npm run build`，或直接用 `.\build.ps1`。

**Q: 改了前端代码，重新编译 exe 后页面没变**

`npm run build` 没有重新执行，或者执行顺序反了。`go:embed` 是编译期打包，必须**先构建前端再编译 Go**。直接用 `.\build.ps1` 最稳妥。

**Q: 我想把桌面推给别人看，但不希望对方能操作我的电脑**

启动时加 `-view-only`（[第 5.4 节](#54-直播模式只读广播)）。客户端只能看画面、听声音，
鼠标键盘和剪贴板都会被**服务端**丢弃——对方改前端、或者直接写脚本连 WebSocket 也绕不过。
注意这是整台服务端的开关：开了之后所有客户端都只读。

**Q: 另一台设备打不开页面**

按顺序排查：

1. 服务端有没有打印出监听地址？如果地址是 `127.0.0.1:8339`，那就只有本机能访问，改用 `-addr :8339`
2. 在服务端那台机器上 `ping <对方IP>` 通不通
3. Windows 防火墙：首次运行时如果弹出了网络访问提示，要选**允许**（专用网络）。也可以手动放行：
   ```powershell
   New-NetFirewallRule -DisplayName "webvnc" -Direction Inbound -LocalPort 8339 -Protocol TCP -Action Allow
   ```
4. 确认两台设备在同一网段（注意有的机器挂着 VPN，会走错网卡）

**Q: 点「粘贴文本」提示浏览器不在此地址提供剪贴板接口**

浏览器的安全模型：`navigator.clipboard` **只在 https、`localhost`、`127.0.0.1` 下存在**。用局域网 IP 或
IPv6 地址以明文 http 打开页面时，这个接口根本不存在，不会有权限弹窗，也无法通过任何设置打开。

四种解决办法，任选一个：

1. **服务端和浏览器在同一台机器上时，直接用 `http://localhost:8339` 打开**（`localhost` 算安全上下文，
   局域网 IP 不算）——点按钮时提示里写的那个 URL 就是它；
2. **配上证书走 https**（`-tls-cert` / `-tls-key`，见[第 5.1 节](#51-直接启用-httpswss)），
   任何地址都变成安全上下文，这是从别的设备访问时的正路；
3. **改用 `Ctrl+V`**，它在任何地址下都能用——没有安全上下文时它会退回监听 `paste` 事件，
   从事件本身拿到文本（事件携带文本，不受这条限制）；
4. **从别的设备访问、又不想弄证书时**，用 SSH 端口转发或 nginx 把地址变成 `localhost`——
   见[第 5.3 节](#53-明文-http-下拿回剪贴板把访问地址变成-localhost)。

> 「粘贴文本」（`Ctrl+V`）和「获取远程文本」（`Ctrl+C`）对这条限制的敏感程度不同：
> 前者有 `paste` 事件可以兜底，**后者需要的是写入接口，而写入没有事件可以兜底**。
> 所以明文 http 下「获取远程文本」和 `Ctrl+C` 是真的用不了，只能走上面第 1、第 2 或第 4 条。

**Q: `Ctrl+V` 粘贴没有反应**

先看状态条有没有回显**「已粘贴 N 个字符」**：

- **没有回显** → 本机这边就没发出去。确认按的时候焦点在页面上（不是别的程序），页面也不是停在登录页。
  如果状态条显示的是「本机剪贴板没有文本」，说明复制那一步没成功——回本机先复制一次。
- **有其他提示** → 按提示处理。`剪贴板内容过大` 是超过了 256 KB；`远程剪贴板写入失败：…` 说明远程
  剪贴板被别的程序占着，**这时远程会粘出它原有的旧内容**。
- **有回显但远程没反应** → 剪贴板已经推过去了，问题在远程那台机器上**粘贴落到了哪个窗口**。粘贴前先在
  画面上点一下目标窗口（比如记事本、输入框）再按 `Ctrl+V`。浏览器和服务端是同一台机器时尤其要注意
  这点——窗口没点对时，粘贴会落在浏览器自己身上。

**Q: 在远程按 `Ctrl+C`，本机剪贴板里没有东西**

按顺序排查：

1. **状态条有没有回显「已复制 N 个字符到本机」？**
   - **完全没有** → 多半是明文 http 打开了页面（见上一条），`Ctrl+C` 这种写入剪贴板的能力在那种地址下
     不可用。状态条会提示一次，**每个会话只提示一次**，之后不再重复。
   - **提示「远程剪贴板里没有文本」** → 远程那边其实没复制到文本。远程复制的是**图片或文件**，
     或者是空选区。本版本只搬运纯文本。
2. **有回显，但粘出来是别的内容** → 状态条上的字样是判断依据：回显说明本机剪贴板**已经被改写**了。
   如果粘出来还是旧的，检查是不是在别的窗口粘贴、或者那个程序自己缓存过剪贴板。

> **远程用右键菜单复制**（没有按 `Ctrl+C`）时，客户端不知道发生了复制，不会自动拉取。
> 点工具栏的「获取远程文本」按钮手动拉一次，它和 `Ctrl+C` 走的是同一段逻辑。

**Q: 怎么用 IPv6 地址访问？**

**默认就支持，不用加参数。** 默认的 `-addr :8339` 同时监听 IPv4 和 IPv6，启动横幅里的
`IPv6 访问  http://[2001:db8:...]:8339` 那几行就是可以直接抄的地址。

抄的时候**方括号不能丢**——`http://[2001:db8:abcd:1234:5678:9abc:def0:1234]:8339`，不要写成
`http://2001:db8:...:8339`。这是 URL 标准的要求（IPv6 地址里的冒号和 `主机:端口` 的分隔符会撞车），
浏览器少一个方括号就直接报解析失败，和本程序无关。

如果对方设备连 IPv4 地址能通，那就不必折腾 IPv6，两个是并列的入口。

**Q: 启动横幅里有 IPv6 地址，但连不上**

按顺序排查：

1. **抄全地址**，包括方括号。少方括号是这里最常见的错误
2. **对方设备自己有没有 IPv6？** 很多内网只有 IPv6 出口没有入站，或者对端压根没分配 IPv6 地址。
   在对方设备上访问 `http://test-ipv6.com` 之类的站点确认一下
3. **`fe80::` 开头的地址横幅里不会列出**，因为链路本地地址必须带上网卡作用域才能用
   （形如 `http://[fe80::1%2516]:8339`，那个 `%16` 是网卡序号，每台机器不同）。局域网内请优先用横幅里
   列出的全局 IPv6 地址，例如 `240e:` / `2409:` 开头的
4. **防火墙**：第 3 条给的放行命令同时覆盖 IPv4 和 IPv6，不需要为 IPv6 单独加一条
5. 想只从 IPv6 访问、避免 IPv4 暴露面，用 `-addr [::]:8339`；只想本机 IPv6 调试用 `-addr [::1]:8339`

**Q: 画面很卡 / 延迟高**

优先交给自动降级：`-max-bitrate 2M` 让服务端自己找平衡点。要手动固定，按影响从大到小依次调低：`-scale 0.75`、`-quality 50`、`-fps 10`。先在能接受画质的前提下压低带宽，再看帧率。

**Q: 状态条显示 `JPEG 帧内`，是不是没启用帧间压缩？**

多半是页面走的是明文 `http://`。WebCodecs 的 `VideoDecoder` 只在**安全上下文**里存在，所以这种页面上
浏览器不会声明自己能解 H.264，服务端只好退回 JPEG——功能上没有任何问题，就是费带宽。
解决办法：配 `-tls-cert` / `-tls-key` 走 HTTPS，或者用 `http://localhost` 访问。启动横幅里会写明
这台机器会用哪条路；`-codec h264` 可以强制要求帧间，此时连不上的浏览器会收到一条说明原因的拒绝。

**Q: 状态条显示 `H.264 帧间`，但 `已限速` 里的质量百分比不见了**

这是对的。帧间模式下 JPEG 质量参数对编码器不起作用，只有帧率是码率控制器能压的旋钮，
所以那里只显示帧率——显示一个变了也不影响任何东西的百分比只会误导人。见[第 3.1 节](#31-带宽调优)。

**Q: 明明没动，为什么码率不是 0？**

静止检测是**逐字节**比较整帧，任何一处像素变化都会让整帧重发。常见「看不见的运动」：闪烁的文本光标、走字的时钟、任务栏动画、后台视频、正在滚动的聊天窗口。鼠标指针移动**不会**触发重发（GDI 截不到光标）。

想看当前是否判定为静止，看状态条的「静止」标记，或 `GET /api/stats` 的 `idle` 字段。想确认静止检测本身是否生效，前后对比一下：

```powershell
.\webvnc.exe -static-skip=false   # 关闭静止跳过，静止时也照常推流
```

**Q: 画面变糊了 / 帧率掉了，是出问题了吗？**

这是码率控制在正常工作，不是故障。状态条会用琥珀色标出当前生效的「质量% / 帧率」，并显示实测码率。想要不同取舍：

- 觉得糊：改用 `-priority quality`，让它优先降帧率保住清晰度；
- 觉得卡：保持默认 `-priority fps`，牺牲清晰度保住流畅度；
- 抬高质量下限：`-min-quality 45`（代价是可能顶不住上限）。

如果日志出现 `still over the bitrate target at the lowest quality and frame rate`，说明已经降到底还是超预算。此时只有 `-scale` 能继续降——它是唯一能减少要编码的像素数量的开关，码率控制器够不着它。

**Q: 设置了 `-max-bitrate`，为什么还是会短暂超出？**

它是**软上限/目标值**，不是硬性限流器。画面突然剧烈变化时，编码器要到下一个统计周期（1 秒）才知道超了，随后按超出程度一次降 1~3 档，通常 2~3 秒内收敛回目标区间。另外上限约束的是**服务端总出口**，多客户端时是所有客户端码率之和。

**Q: 鼠标位置点不准**

只支持**主显示器**，多显示器是二期功能。另外确认没有以"兼容模式 / 高 DPI 缩放"方式启动 exe——程序自己会设置 DPI 感知，不需要额外配置。

**Q: 中文打不出来，或者候选框不出现**

1. 确认焦点在远程画面上：
   - **桌面**：**点一下画面**就能拿回焦点（点工具栏按钮不会抢走焦点，但如果切出去过就需要重新点一下）
   - **手机/平板**：**点一下工具栏「键盘」**。这里的点画面**不再**接管键盘
     （默认关闭，见[第 4.1 节](#41-手机平板操作触摸手势)）——照着桌面那条做，会以为功能坏了
2. 确认本机输入法已开启（`Shift` 或 `Ctrl+空格` 切换）。**手机/平板还必须先打开「键盘」开关**：
   输入法要挂在那块隐藏的 `<input>` 上，而关着键盘时它不持有焦点
3. 候选框显示在**本地浏览器**上，不在远程画面里，这是设计如此

**Q: 按 `Ctrl+V` 粘贴的是远程的剪贴板？**

**是，这是设计如此。** `Ctrl+V` 会把本机剪贴板**推给远程**，然后让远程执行它自己的粘贴；
在远程按 `Ctrl+C` 又会把远程剪贴板**取回本机**。两个方向合起来就是一份**两边共享的文本剪贴板**
（细节见[第 6.3、6.4 节](#63-粘贴ctrlv把本机剪贴板送到远程)）。

这带来一个必然的副作用：**在远程粘贴会覆盖掉远程原有的剪贴板内容**。要让远程应用执行"它自己的"粘贴，
就只能走它自己的剪贴板，没有别的办法。

只支持纯文本。图片、文件、HTML 等格式不搬运。

**Q: 手机上点一下，结果先点了一次才拖起来**

这是**已知取舍**，不是 bug。第一下点按立即生效（不做 250ms 的延迟判定），这样普通单击
没有任何等待感；代价是「点一下再按住」这个拖拽手势，第一下会先真的点一次。
手感细节见[第 4.1 节](#41-手机平板操作触摸手势)。

**Q: 手机上手指滑动了，但远程的指针没动**

多半是选在**鼠标模式**（相对移动）——此时指针按手指的位移移动，起点是远程屏幕中心，
而且远程画面里不含光标，看不到它挪到哪儿去了。切到**触屏模式**就是点哪到哪。
工具栏那组「鼠标 / 触屏」按钮只在检测到触摸屏时出现。

**Q: 手机上长按弹出了系统的选择气泡，右键发不出去**

画面上已经关掉了 `-webkit-touch-callout` 和文本选中，正常情况下不会弹。如果仍然弹出，
多半是页面被 iOS 的「在浏览器中打开」以外的容器（比如某些 App 的内置 WebView）接管了，
换 Safari / Chrome 直接打开即可。

**Q: 为什么 `Alt+Tab` / `Ctrl+Alt+Del` 没反应？**

被**本地操作系统**在底层截获了，浏览器根本收不到这个事件，程序也就无从转发。`Ctrl+Alt+Del` 还额外受 Windows 的 UIPI 保护限制，普通进程无法用 `SendInput` 模拟。属于系统限制。

**Q: 日志全是乱码**

程序启动时会主动把控制台切到 UTF-8（代码页 65001）以正常显示中文。如果你是把输出**重定向到文件**再用旧工具打开，需要用 UTF-8 编码读取：

```powershell
Get-Content run.log -Encoding utf8
```

**Q: 支持 HTTPS 吗？**

支持。把证书和私钥一起传给 `-tls-cert` / `-tls-key` 即可，不传就是明文 HTTP（默认）。
详见[第 5.1 节](#51-直接启用-httpswss)。注意用**证书覆盖的域名**访问，用 IP 或 `localhost`
打开会报证书错误——证书核对的是地址栏里的名字，不是连到了哪台机器。

也可以继续用 Caddy / nginx 反向代理终止 TLS，见[第 5.2 节](#52-用反向代理终止-tls)。

**Q: 点了「开启声音」，还是听不到**

按顺序排查：

1. **远程那台电脑自己在出声吗？** 采的是它的播放回环，它不响这边就没有东西可放
2. **远程的默认播放设备对不对？** 机器上挂多个渲染端点时采的是 Windows 里设成**默认**的那一个，
   被 Steam Streaming Speakers、虚拟声卡之类占着就会采到一片安静。去「设置 → 系统 → 声音」改回真实扬声器
3. **远程的系统音量/静音状态**：确认没被静音、音量不是 0
4. **看状态条**：「声音 待机」= 连接正常、远程确实没在出声；「无声」后面跟着失败提示 = 连接根本没建起来
5. **服务端是不是用 `-audio=false` 起的？** 那样 `/ws/audio` 直接返回 404

**Q: 声音比画面慢一点 / 对不上口型**

PCM 从采集到出声要经过约 100ms 的抖动缓冲——不留这点余量，网络稍微一抖就是一声断音。另外画面和声音
走两条**没有共同时钟**的连接，不保证严格同步。远程协助够用（差不到一帧），对口型不够。详见
[第 8 节](#8-通信协议)。

**Q: 开了声音，画面就变糊/掉帧了**

这不是 bug，是 `-max-bitrate` 的语义决定的：声音是恒定 1.4~1.5 Mbps 的独立码流，而且**计入总出口上限**。
设 `-max-bitrate 2M` 时它一口气吃掉一大半，视频只剩约 589 kbps。想两样都要，就把上限抬到
`-max-bitrate 4M` 之类，或者用 `-scale 0.75` 先减少要编码的像素。详见[第 3.3 节](#33-声音与带宽)。

**Q: 为什么安静时状态条显示「声音 待机」，而不是 0 kbps？**

因为安静时服务端是**停发**的，而不是发一堆静音数据。直接显示 0 kbps 会让人以为坏了，所以说「待机」——
和画面静止时显示「静止」是同一个道理。

**Q: 想确认服务有没有在正常推流**

```powershell
Invoke-RestMethod http://127.0.0.1:8339/api/stats
# clients      : 1
# fps          : 14.9    # 实测发送帧率（画面静止时会掉到 0）
# targetFPS    : 15      # 降级后当前生效的目标帧率
# quality      : 65      # 当前生效的 JPEG 质量
# kbps         : 820     # 视频实测出口码率
# idle         : False   # 画面是否静止
# limited      : False   # 是否已被码率控制降级
# atFloors     : False   # 是否已降到下限仍超预算
# audioClients : 1       # 正在听声音的连接数（没开声音就是 0）
# audioKbps    : 1411    # 声音实测出口码率（安静停发时为 0）
# audioIdle    : False   # 声音是否处于停发状态
```

## 11. 已知限制与后续计划

### 当前版本（一期）的边界

- **只支持主显示器**，多屏拼接/选择是二期功能
- **只捕获桌面画面**，硬件加速独占全屏的应用（部分游戏、全屏视频）可能抓到黑屏
- **剪贴板只搬纯文本**：两个方向都通了（`Ctrl+V` 送到远程、`Ctrl+C` 取回本机），但**图片、文件、
  HTML 等格式不搬运**——远程剪贴板里是图片或文件时会提示"没有文本"。另外**远程复制不会自动改写
  本机剪贴板**，是按下 `Ctrl+C`（或点「获取远程文本」）时才拉取
- **明文 http 下只能"送出去"，不能"取回来"**：读取剪贴板有 `paste` 事件可以兜底，写入没有。所以没配
  https 又想用 `Ctrl+C` 取回远程文本，只能换 `http://localhost` 或配证书，详见[第 6.4 节](#64-复制ctrlc把远程剪贴板取回本机)
- **明文 http 下拿不到帧间压缩**：WebCodecs 的 `VideoDecoder` 只在安全上下文里存在，所以浏览器在
  `http://` 页面上不会声明能解 H.264，服务端于是退回帧内 JPEG——行为和加这个功能之前一模一样。
  想要帧间压缩必须配 HTTPS（或走 `http://localhost`），详见[第 8 节「能力协商」](#能力协商)
- **帧间压缩的客户端解码是 WebCodecs，不是 MSE**：见下方「二期」中关于纯 HTTP 场景的说明
- **声音不压缩，带宽恒定在 1.4~1.5 Mbps**，且**计入 `-max-bitrate`**。开声音会明显挤压画面，
  详见[第 3.3 节](#33-声音与带宽)
- **没有音画同步**：画面和声音是两条独立连接，没有共同时钟，浏览器只是把收到的 PCM 按自己的时钟
  连续排下去。远程协助够用，对口型不够
- **只采默认播放设备**，不能选设备，也不会跟着"默认设备切换"自动换——机器上挂着虚拟声卡
  （Steam Streaming Speakers 之类）时可能采到一片安静，需要先把默认输出改回真实硬件
- **不做麦克风采集**：只做系统回环（听远程在放什么），不监听远程房间里的声音。这是有意为之，
  隐私含义完全不同
- **服务端不做音量控制**：只有开/关，没有增益调节
- **声音安静时停发**，恢复瞬间会有一次极短的缓冲欠载。这是「静音时不占带宽」换来的代价
- **输入不做仲裁**：多个客户端同时连接时，任何一方的输入都会生效，可能互相干扰。适合一对一协助，不适合多人协作
- **直播模式（`-view-only`）是整台服务端的开关，不能按连接区分**：开了之后**所有**客户端都只读；
  服务端目前也没有任何客户端身份概念（只记录来源 IP），做不到「甲能操作、乙只能看」。
  同一时间想有人能操作，就不要开这个参数
- **不带证书时是明文 HTTP**：口令会以明文经过网络，需要加密就传 `-tls-cert` / `-tls-key`（见[第 5.1 节](#51-直接启用-httpswss)），或自己用反向代理
- **TLS 只保护传输，不改变鉴权**：口令门禁仍是唯一的访问控制
- **`Alt+Tab` / `Ctrl+Alt+Del` / `Win` 组合键**受系统限制无法转发
- **触屏设备的软键盘默认关闭**：点画面只操作远程，打字要先点工具栏「键盘」。这不是没做适配，
  而是刻意的默认——手机上一次误弹的键盘要占掉半个屏幕，详见[第 4.1 节](#41-手机平板操作触摸手势)。
  关着的时候本机输入法用不了（硬件键盘不受影响），要打中文先把键盘打开
- **触摸的「鼠标模式」（相对移动）没有指针位置反馈**：远程画面里不含光标（见下一条），
  所以手指滑动时看不到指针挪到了哪里，只能靠画面上的悬停高亮判断。这是「相对定位」和
  「画面无光标」两件事叠在一起的结果，要解决得先补上远程光标合成，详见[第 4.1 节](#41-手机平板操作触摸手势)
- **远程画面里看不到鼠标指针**：GDI 的 `BitBlt` 不合成光标，所以截到的帧里没有指针。这是既有行为，不是静止检测引入的（顺带一提，也正因如此，指针移动不会让静止检测误判为「画面有变化」）
- **码率上限是软上限**，不是硬限流，突发时会短暂超出，详见[第 3.1 节](#31-带宽调优)
- **IPv6 的失败锁定按 /64 前缀计数**：同一 /64 内的所有设备共享锁定状态。这是为了堵住「换个地址继续猜」的漏洞，代价是同一网段的邻居可能被误伤，详见[第 5 节](#5-安全须知务必阅读)
- **链路本地 IPv6 地址（`fe80::` 开头）不会出现在启动横幅里**：它们必须带上每台机器各不相同的网卡作用域才能访问，列出来只会让人抄错。局域网内请用全局 IPv6 地址
- **有公网 IPv6 时本服务可能直接从外网可达**：IPv6 通常没有 NAT 遮挡，是否暴露取决于路由器的入站策略，而不是本程序。详见[第 3.2 节](#32-ipv6-访问)

**以上是 Windows 版本的边界。Linux 版本另有：**

- **Wayland 原生窗口抓不到**：程序连的是 X 服务器，在 Wayland 桌面上只能看到跑在 XWayland 里的
  X11 程序。要覆盖 Wayland 原生窗口需要 `xdg-desktop-portal` + PipeWire，见[第 2.5 节](#25-平台支持)
- **没有声音采集**：`NewAudioCapturer` 返回 `ErrUnsupportedAudio`，页面上是明确的"不支持"提示，不是静默无声
- **没有剪贴板**：`Ctrl+C` / `Ctrl+V` 两个方向都不通，返回 `ErrUnsupportedClipboard`。
  中文输入**不受影响**——它走的是 XTEST 的按键序列，不经过剪贴板
- **没有帧间压缩**：Linux 侧没有 H.264 编码器实现，所以 `-codec auto` 直接落到帧内 JPEG，
  而 `-codec h264` 会以"这台机器没有帧间编码器"启动失败。带宽因此比 Windows 侧高一截
- **只抓主屏幕**：X11 的多屏是 Xinerama/RandR 拼接在一个根窗口里，程序抓的是整个根窗口，
  也就是所有屏幕的并集，不能单独选一块
- **根窗口色深必须是 24 或 32 位**：16 位（RGB565）和 8 位的根窗口没有对应的通道交换，
  程序会明确报错而不是送出一张颜色错乱的画面
- **`Alt+Tab` / `Ctrl+Alt+Del` 同理受限**：由本地系统或 Wayland 合成器在更底层截获

> **跳过的东西要看得见。** 没有 `DISPLAY` 时，`server` 的 X11 集成测试和根目录那几条端到端测试
> 都会 `t.Skip` 并说明原因（`go test -v` 里是 `--- SKIP`），而不是变成一个安静的 PASS——
> 一个看不见的跳过和通过长得一模一样，而这两件事的意义完全不同。
> **想在 CI 里得到完整覆盖，就跑 Xvfb**：一个 `Xvfb :99 -screen 0 1280x800x24` 就是一台真的
> X 服务器，协议、共享内存、XTEST 全是真的，只是屏幕上的内容由测试自己画。

> **`go vet` 在 Linux 上有一条已知告警：** `server/capture_linux.go` 的
> `possible misuse of unsafe.Pointer`。这是**有意为之且安全的**，不是待修的问题——
> 那处转换把 `shmat` 返回的地址变成切片，而 System V 共享内存不受 Go 运行时管理，
> 不会被 GC 搬运或释放。`go vet` 的规则是**语法性**的：只要看到一个 `uintptr` 变
> `unsafe.Pointer` 就报，它无从知道这个 `uintptr` 来自 `shmat`。详细理由写在那个函数上方的注释里。

> `server/hub_test.go` 里的测试会**真的抓屏并真的移动鼠标光标**（用来验证 `SendInput` 确实到达了系统），跑完后会把光标位置还原。测试针对的是真实桌面，所以鼠标位置断言带有容差和重试——如果你正在手动动鼠标，有可能偶发失败，重跑即可。
>
> `server/ws_stream_test.go` 和 `server/capture_loop_test.go` 反过来：它们注入一个脚本化的假 `Capturer`，再用真实的 WebSocket 传输跑完整条推流链路。因为画面内容完全由测试控制，静止停发、降级收敛这类断言是**确定性**的，不受当前桌面上在跑什么影响。
>
> `server/ws_audio_test.go` 同理，注入一个脚本化的假音频设备（能演「有声 / 无声」），验证格式握手先于数据包、每个包恰好是 3528 字节、静音时真的停发且 `audioStats` 报告 idle、恢复后自动续传，以及音频对视频码率预算的扣减与释放。**不需要声卡，也不会发出任何声音。**
>
> `server/auth_test.go`（IPv6 失败锁定的 /64 归并）、`server/frame_diff_test.go`、`server/bitrate_test.go` 是纯逻辑测试，不碰屏幕也不碰网络，任何平台都能跑。
>
> `server/audio_test.go`（格式转换、20ms 分包、静音看门狗、音频对码率预算的扣减）同样是无 build tag 的纯逻辑测试——
> 这也是为什么音频的 DSP 部分被刻意从 `audio_windows.go` 里拆了出来。需要 Windows 的只有
> `server/audio_windows_test.go`，它断言 COM 结构体的字段偏移、GUID 的字节序、HRESULT 的符号判定
> 这些**写错不会崩、只会安静地读错**的地方。
>
> `server/video_test.go` 也是免桌面的，而且**在有编码器和没编码器的机器上都跑**：它只断言「答案的形状」，
> 不断言答案本身（`-codec h264` 允许失败，`auto` 不允许）。关键帧重放那条规则走真实的 WebSocket，
> 但把 hub 的采集循环停掉，于是线上只会有测试自己放进去的帧——这正是它能在**没有 H.264 编码器**的
> 机器上覆盖帧间那一半规则的原因：那些字节只被转发，从不解码。
>
> `cmd/mfprobe/` 是个诊断工具，不是测试：它会枚举本机上**所有**的 H.264 编码器 MFT，逐个激活、
> 报告是否异步、用同一份配置各跑一遍，并把四种码率控制模式横向对比成一张表。换机器排查
> 「为什么这台没有帧间压缩」时先跑它：
>
> ```powershell
> go run ./cmd/mfprobe            # 默认跑 90 帧
> go run ./cmd/mfprobe -frames 300
> ```
