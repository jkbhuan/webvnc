1. 剪贴板双向同步

1.1 问题

通过 https 连接点击「粘贴文本」按钮有效果了，但是 Ctrl+C/V 还是不行，而且文字复制不出来。

原本只有一个方向：点按钮 → 用 text_input 把文字打进远程。这条路径绕开了剪贴板，所以"有 input 框的地方能粘贴"，但任何依赖剪贴板本身的场景都不行——右键菜单里的「粘贴」、需要重新读取剪贴板的程序、以及最关键的 Ctrl+V 习惯。

1.2 方案

先定两个方向：

  • 送出（本机 → 远程）：Ctrl+V 时把本机剪贴板文本推到远程剪贴板，再在远程按一个真正的 Ctrl+V。
  • 取回（远程 → 本机）：Ctrl+C / Ctrl+X 时按键照常转发（远程应用正常复制），松开按键时再把远程剪贴板拉回本机。

为什么选"推送 + 合成 Ctrl+V"而不是继续用 text_input：合成按键之后，走的是远程应用自己的粘贴路径。这意味着 URL 会变成链接、表格会变成真表格、终端里会走终端的粘贴语义。text_input 只是把字符敲进去，永远做不到这些。

协议新增：

上行（浏览器 → 服务端）：
  { "type": "clipboard_pull" }                    // 取回远程剪贴板
  { "type": "clipboard_push", "text": "..." }     // 写入远程剪贴板

下行（服务端 → 浏览器）：
  { "type": "clipboard", "op": "pull"|"push", "ok": true, "text": "...", "error": "" }

ok: false 只保留给真正的失败（比如剪贴板被锁死）。空 text 配 ok: true 是"远程剪贴板里没有文本"这个正常状态，两者在 UI 上必须给不同的话术。

1.3 验证

新建了一个临时的 live 测试文件（5 个测试，跑完即删）。最关键的一条是：

TestClipboardLiveWriteVisibleToAnotherProcess —— 通过真的 websocket 推一段中文进去，然后用另一个进程的 PowerShell Get-Clipboard 读回来。

这条测试是整轮里唯一有决定性的验证。原因见 坑 8：用自己的读函数去读自己写的内容，只能证明自洽，不能证明写对了。

1.4 踩过的坑

坑 1OpenClipboard(NULL) 的文档是错的

三处微软文档都写着：用 NULL 作为 hwnd 打开剪贴板，会让 EmptyClipboard 把剪贴板所有者设成 NULL，从而"导致 SetClipboardData 失败"。

按文档的推论，必须建一个隐藏的 HWND_MESSAGE 窗口来当 owner，为此还要 runtime.LockOSThread 加一个专用 goroutine 和 channel 来收发窗口消息。复杂度很大。

实测（Windows 11 build 26100）：直接就能用。

所以这里的处理是：不定案于文档，定案于实证。写了一个跨进程读回的测试（1.3），通过就不要那个隐藏窗口。

判断依据是失败的形态：如果这条路真的走不通，表现是响亮的——SetClipboardData 返回 0，用户在状态栏看到"远程剪贴板写入失败"。它不会静默地写错内容。为一个会大声报错、且实测不存在的风险，预先引入一个窗口 + 专用线程 + 消息循环，不划算。

这条已经单独记进项目记忆（win32-clipboard-null-owner-works.md），防止未来某一轮"照着文档把它修好"。

坑 2LazyProc.Call 永远返回非 nil 的 error，且这个 error 会说谎

这是整轮里最危险的一个发现。

syscall.LazyProc.Call 的签名是 (r1, r2 uintptr, lastErr error)，lastErr 永远非 nil。当调用失败但系统没有设置 last error 时，它返回 Errno(0)——而 Errno(0).Error() 是：

The operation completed successfully.

原来的代码用 %w 包了这个 error。这句话会原样出现在浏览器状态栏里。用户看到"操作已成功完成"，然后去找为什么没成功——往一个完全错误的方向找。

修法：加了个 winErr()，把 errno 判出来显示数字错误码：

func winErr(err error) string {
	var errno syscall.Errno
	if !errors.As(err, &errno) {
		return err.Error()
	}
	if errno == 0 {
		return "系统未报告错误码"
	}
	return fmt.Sprintf("%v（错误码 %d）", errno, int(errno))
}

五个调用点全部从 %w 改成 %s + winErr(err)。

通用教训：一个措辞是"成功"的错误，比一个措辞含糊的错误危险得多。

坑 3剪贴板是一把全局独占锁，而且不可重入

剪贴板同一时刻只能被一个进程打开。更麻烦的是它在同一进程内也不可重入——第二个线程会失败，而不是排队。

浏览器可以同时开多个连接，两个客户端完全可能同时按 Ctrl+C。

修法：进程级 sync.Mutex 把每一次 open/close 括起来，配 10 次重试 × 20ms 退避：

var clipboardMu sync.Mutex

func openClipboard() (func(), error) {
	clipboardMu.Lock()
	for attempt := 0; attempt < clipboardOpenAttempts; attempt++ {
		ok, _, _ := procOpenClipboard.Call(0)
		if ok != 0 {
			return func() { procCloseClipboard.Call(); clipboardMu.Unlock() }, nil
		}
		if attempt < clipboardOpenAttempts-1 {
			time.Sleep(clipboardOpenBackoff)
		}
	}
	clipboardMu.Unlock()
	return nil, ErrClipboardBusy
}

注意返回的是个 func() 而不是直接返回 error——关闭必须和加锁配对，用闭包可以保证 defer 一定成对执行。

原来的重试循环本身也能让输的一方最终成功，但那要等 200ms 才失败。加锁把"200ms 后报错"变成"几毫秒后成功"。

坑 4SetClipboardData 成功后内存所有权转移给系统

// 成功：系统接管了这块内存
// 失败：必须自己释放，否则泄漏

顺序也容易错：块必须在 CloseClipboard 之前解锁（GlobalUnlock），而 CloseClipboard 之后就不能再碰它了。

坑 5GlobalSize 只是上界，块不保证以 NUL 结尾

读的时候不能假定"拿到指针就能当字符串用"。必须在 GlobalSize 给的范围内扫描，而不是依赖结尾的 NUL。

坑 6上限必须小于 gorilla 的读上限

maxMessageSize = 1 << 20（1 MiB）是 gorilla 的读限制。超了不是返回错误，而是直接关闭连接。

所以剪贴板上限取 MaxClipboardBytes = 256 << 10（256 KB），刻意的四分之一：

// It is deliberately a quarter of maxMessageSize. That limit is enforced by the
// ...
const MaxClipboardBytes = 256 << 10

留出四倍余量是因为上限按字节算，而剪贴板内容按 UTF-16 单元算，JSON 转义还会再膨胀。

坑 7Ctrl+C 的取回必须挂在 keyup，不是 keydown

Windows 的输入队列是每线程 FIFO。所以：

  • keydown 到达远程 → 应用处理它 → 应用写剪贴板 → 然后 keyup 才到达。

如果在 keydown 时就拉剪贴板，拉到的还是上一次的内容。挂在 keyup 上，应用才保证已经写完了。

坑 8只读回自己写的内容，等于什么都没验证

这条单独列出来，因为它是验证方法论上的坑，不是代码坑。

最初的自测是"写进去，再用我们自己的读函数读出来，内容一样 → 通过"。但这只能证明读写自洽：如果两个函数在同一个地方一起写错了（比如字节序、编码），它会照样通过。

决定性的验证必须换一个主体：用 PowerShell 的 Get-Clipboard 在另一个进程里读。

坑 9GitHub 的锚点是"删标点"，不是"把标点换成连字符"

改 README 时算错了两处锚点。我一开始按"标点 → 连字符"推理，写出了 #63-粘贴ctrlv-把本机剪贴板送到远程。

正确的算法是：小写 → 删除所有非字母/数字/空格/连字符/下划线/CJK 的字符 → 空格换成连字符。标点是直接删掉，不留痕迹。

所以 ### 6.3 粘贴（Ctrl+V：把本机剪贴板送到远程） 的实际锚点是：

#63-粘贴ctrlv把本机剪贴板送到远程

. 空格 （ ） ： + 全部消失，Ctrl+V 的 + 也没了，所以是 ctrlv 连在一起。

验证方法是拿一个已经存在且确定能用的锚点反推：### 5.1 直接启用 HTTPS（wss://） → #51-直接启用-httpswss（. 删掉变成 51，// 和 : 删掉变成 wss，HTTPS 小写）。对得上，算法就对了。

2. 滚轮方向反了

2.1 问题

我发现滚轮操作是反的，修改一下。

2.2 根因：两个轴的约定一个反、一个不反

这是整轮改动里唯一的真实 bug，而它的狡猾之处在于不对称：

轴浏览器Windows关系
竖直 deltaY > 0 = 向下滚 MOUSEEVENTF_WHEEL 正值 = 向上滚 相反
水平 deltaX > 0 = 向右滚 MOUSEEVENTF_HWHEEL 正值 = 向右滚 一致

所以只有竖直轴需要翻转。

2.3 方案

翻转放在服务端，而且写在注释里说明为什么不放在浏览器：

func (c *Client) handleWheel(msg *clientMsg) error {
	c.wheelAccX += msg.DeltaX
	c.wheelAccY -= msg.DeltaY   // 只有这里翻转

	unitsX := takeNotches(&c.wheelAccX)
	unitsY := takeNotches(&c.wheelAccY)
	if unitsX == 0 && unitsY == 0 {
		return nil
	}
	return c.hub.inj.Wheel(unitsX, unitsY)
}

理由是保持线上格式为浏览器原始像素——协议层只做搬运，不做解释，这样以后要接别的客户端（比如原生 App）时，两边对"发什么"的理解是一致的。

换算常量：wheelPixelsPerNotch = 100.0（100 浏览器像素 = 1 格），一格 = wheelDelta = 120 个 Windows 单位。不足一格的余量累积到下一次，所以触控板的小步滚动不会丢。

2.4 验证：证明测试有牙齿

新增 TestWheelDirection，把两个轴的方向都钉住：

if err := c.handleWheel(&clientMsg{DeltaY: wheelPixelsPerNotch}); err != nil { ... }
if inj.wheelY != -wheelDelta { ... }   // 浏览器向下滚 → Windows 必须是负

// 水平两个约定本来就一致，所以这个**不能**跟着竖直一起被翻转
if inj.wheelX != wheelDelta { ... }

关键动作：把 -= 临时改回 += 重跑，确认它以用户报的症状失败：

a browser scroll down produced 120 Windows units, want -120

然后改回来。这一步确认了测试不是空的——如果它改坏了也照样通过，那它就只是个装饰。

2.5 附带修掉的债

3. 手机触摸操作

这一轮最大，也最值得写下来。

3.1 需求

我希望如果是手机端连接，能模仿 mstsc 的操作逻辑，长按表示右键，点一下松开再按下表示按住左键，鼠标移动逻辑也参考 mstsc，可以在界面选择鼠标模式和触屏模式。鼠标模式手指在屏幕上滑动只是操作指针往与手指相同的方向移动，而不是手指在哪鼠标就在哪，而触屏模式就像手机一样，点哪就是哪。

两个需要用户拍板的取舍，都确认了：

  • 第一下点击立即生效（不做 ~250ms 的延迟判定）。响应无延迟，代价是每次拖拽前会先多出一次单击。
  • 双指滚动这次一起做。否则手机端只能靠拖动滚动条。

3.2 关键设计决定

决定 1：手势状态机独立成纯模块

RemoteScreen.vue 已经 1200+ 行，而这个功能的核心复杂度是「模式 × 手势 × 手指数」的组合。混进组件既难读，也没法验证。

而且前端没有任何测试框架（package.json 里只有 vue-tsc / vite，src 下没有任何 *.test.ts）。

于是新增 frontend/src/touch.ts：不 import 任何 DOM、时钟由外部注入、输出是一个 action 列表。这带来两个好处：

  1. 逻辑可以脱离浏览器验证（见 3.5）。
  2. 计时器变成可以合成时间戳驱动的——长按和拖拽起手不依赖 setTimeout 的内部状态，可以用 tick(合成时间) 精确地走到"差 1ms 还没触发"和"刚好触发"。

决定 2：模式只影响触摸和手写笔，物理鼠标永远绝对定位

用 e.pointerType 区分。'mouse' 在任何模式下都保持原来的绝对行为。

理由：把真实鼠标改成相对移动是反直觉的，平板接了蓝牙鼠标的用户会立刻觉得"鼠标坏了"。

决定 3：相对位移的换算基准是"画出来的图像"，不是 canvas 元素

remotePx = cssPx × (remoteW / 绘制区域CSS宽度)

即"手指划过整个画面宽度 = 指针走过整个远程桌面宽度"，与 -scale 和窗口大小无关。

注意是绘制区域而不是 canvas 元素——画面是 letterbox 的，用元素宽度会被黑边稀释。

决定 4：双指滚动按浏览器约定发送

与手机一致：双指上滑 = 页面向下滚。所以 wheelDeltaY = -手指位移Y。

这里有个容易重复踩的坑：服务端在 handleWheel 里已经对竖直方向翻转过（第 2 节）。所以前端要按浏览器约定原样发送，不要预先抵消，否则翻两次等于没翻。

3.4 工程实现上的配套

  • 按 pointerId 追踪活动指针（一个 Set 就够）。原来是单指针假设，第二个手指会让它们互相踩。
  • 手势期间跑 25ms 的 setInterval 驱动 tick()，无手势时停掉，不空转。
  • releaseAllButtons()，照 releaseAllKeys 的样子写，接 window blur / visibilitychange / pointercancel。
  • 工具栏：8 个控件在手机宽度下放不下 → flex-wrap + 窄屏隐藏品牌 + @media (pointer: coarse) 下按钮撑到 40px。
  • 模式选择只在 maxTouchPoints > 0 时出现——它对鼠标毫无作用，没必要占位置。

3.5 验证

分两层，两层互补，都不需要手机。

第一层：状态机（42 条断言）

用 npx esbuild 把 touch.ts 转成 js（vite 自带 esbuild，不引入任何新依赖），再用 node 喂合成时间戳，把每条路径跑一遍并打印 action：

单击 / 长按右键 / 点一下再按住拖拽 / 移动起手拖拽 / 两次快速点击 / 滑动超过容差后抬起（不应有单击）/ 双指滚动（含竖直符号）/ 第二指落下时左键正被按住（应补 mouseup）/ 两种模式的差异 / 指针裁剪 / reset / 切换模式。

第二层：真·浏览器（20 条断言）

headless Chrome + CDP，把 WebSocket 在页面里替换成桩，用 Input.dispatchTouchEvent 合成触摸，断言页面实际发出了什么。

这一层才覆盖到单元测试够不着的东西：坐标映射、事件管线、发送顺序、tick 定时器。

几个关键技巧，值得复用：

  • 不需要服务端。桩会回一条 screen 控制消息 + 一个 JPEG。
  • 必须先有一帧被解码才能测。view（绘制矩形）只在 paint() 里算，而 paint() 需要一帧。所以桩必须发一帧真的 JPEG——用页面内 canvas 的 toBlob('image/jpeg') 现做一个，不用内嵌字节。
  • maxTouchPoints 要在 bundle 之前注入（Page.addScriptToEvaluateOnNewDocument 里 Object.defineProperty），否则工具栏那组模式按钮根本不渲染。
  • 相对模式和绝对模式不能靠"增量"区分——两者每步的增量是一样的。必须先让触屏模式把指针停在一个已知位置，再比落点。
  • 完全绕开了本机的工作站焦点争用问题（见记忆 workstation-focus-contention），因为整个过程不碰真实桌面。

3.6 踩过的坑

坑 1拖拽起点错误（状态机测试抓到）

靠移动进入 dragHold 时，触屏模式下没有把指针移到手指处。

后果：拖拽会从"上一次点击所在的位置"开始，然后被手指的第一次移动猛地拽过来。

// 修法：进入 dragHold 时补一个绝对移动
if (this.mode === 'touch') actions.push(...this.absoluteMove(x, y))
actions.push({ kind: 'button', button: 'left', down: true })

顺序也有讲究：先移动，再按下左键。

坑 2点击位置过期（e2e 抓到）

一次轻点在同一个批次里产生 moveTo + click。而 moveTo 走的是 rAF 合并（为了不淹没 socket），于是它可能比 click 晚发——点击落在指针的上一个位置。

修法：任何按键事件之前先 flushMove()：

case 'click':
  flushMove()   // 否则点击会落在指针的上一个位置
  client?.send({ type: 'mousedown', button: a.button })
  client?.send({ type: 'mouseup', button: a.button })
  break

这个 bug 在鼠标路径上也潜伏着（只是实际中 mousemove 总比 mousedown 早很多帧，暴露不出来），一并修了。

通用教训：合并（coalescing）会打乱顺序。任何"延迟到下一帧再发"的优化，都必须在使用它的事件之前显式 flush。

坑 3pointerMove 的 now 参数是死参数

最初 pointerMove(id, x, y, now) 为了和 pointerDown / pointerUp 对称，也接收了时间戳。但编译器直接指出它没被用过。

想了一下：移动本身已经说明了意图，静止才是计时器的事。一个在动的手指会通过"漂移超过容差"取消长按，不需要时钟。

于是删掉参数，而不是留一个 _now 占位。

留一个用不上的参数，比删掉它更贵——它会让下一个人以为这里有时间语义。

坑 4e.preventDefault() 挡不住 iOS 的系统菜单

长按会弹出 iOS 自己的选择气泡，右键就发不出去了。必须在 CSS 上彻底关掉：

.screen-canvas {
  touch-action: none;          /* 原本就有 */
  -webkit-touch-callout: none; /* 长按不弹系统菜单 */
  -webkit-user-select: none;
  user-select: none;
}

坑 5按键有"失焦全松"保护，鼠标键没有

按键早就有 releaseAllKeys() 挂在 window blur 上——切标签页时 Ctrl 不会卡在远程。

但鼠标键没有对应的保护。触摸端一次意外切后台（切标签页、来电、失焦），远程就会一直处于按住左键的状态，用户回来发现整个桌面在跟着手指拖。

修法：加 releaseAllButtons()，并把两者合成 releaseAll()，接上 window blur / visibilitychange / pointercancel。

顺带补了 visibilitychange 的"切走时松手"分支——隐藏标签页里定时器会被降频，手势会冻在半路而按钮还按着。

坑 6单指针假设是隐藏的

原来的 pendingMove / moveScheduled / dropping 全都是单指针假设，第二个手指会让它们互相踩。这是双指滚动的硬性前提，不是可以后补的优化。

这类"隐藏的单实例假设"和剪贴板的"全局独占锁"是同一类东西：代码在只有一个人用的时候完全正确。

坑 7写测试时踩的坑，本身就是信息

我自己写的测试脚本失败了好几次，每一次失败都是真实的语义，不是测试写错那么简单：

  • 两次手势之间必须留够 400ms。否则第二次按下会被认为是"拖拽的起手"（设计的双击窗口），长按测试就没有长按。真机上这也是这个行为——它是设计，只是在测试里咬人。
  • 双指滚动的量是两指的质心位移，所以"一根手指动 50px、另一根不动"只滚 25px。我一开始按 50 写断言，失败了——代码是对的，断言是错的。
  • 鼠标模式下"滑动后抬起"不产生点击。因为移动超过容差就取消了点击判定——这正是触控板 tap-to-click 的行为（滑过之后不点）。我一开始断言它会点，失败了，代码又是对的。

这三个坑的共同点：我的直觉假设比代码更值得怀疑。测试失败时，先问"是不是代码比我以为的更对"。

坑 8测试脚本自身的时序 bug

e2e 最后一轮回归时，"切换模式应该松开按住的键"这条失败了，返回空数组。

原因是我在重构脚本时多加了一句 sleep(600)，把第二次按下推出了 400ms 的双击窗口，于是它变成了一个全新的 press——而 400ms 又不够 500ms 的长按。压根没有按键被按住，自然也没什么可松开的。

教训：同一个测试脚本改了之后要重跑全部，不能只跑被改的那段。

坑 9比例尺要用"绘制区域"而不是"元素"

updateTouchScale() 一开始用的是 canvas.getBoundingClientRect().width。改成按绘制区域算：

const paintedW = (view.dw / canvas.width) * rect.width
gestures.setScale(remoteW.value / paintedW, remoteH.value / paintedH)

顺带发现调用时机也错了：原来在 resizeCanvas() 里 draw() 之前调，而 view 只有 draw() 里才重算，所以拿到的永远是上一次布局的值。移到 draw() 之后。

3.7 与计划的偏差

两处，都是实现时发现计划里没考虑到：

  1. 模式选择只在 maxTouchPoints > 0 时渲染。计划是常驻。但一组对鼠标毫无作用的按钮，挤在已经有 7 个控件的工具栏里，只会造成困惑。
  2. 手写笔（pen）归到触摸一类，跟随所选模式，而不是保持绝对定位。

4. 附：远程画面里为什么看不到指针（调研，未实施）

这一节只是调研结论，没有改代码。

4.1 直接原因

server/capture_windows.go:173 用 BitBlt 从屏幕 DC 拷贝到内存 DC。而光标不在桌面缓冲里——它是独立于桌面像素之外的一层，由显示硬件 / DWM 合成器单独叠加。所以无论怎么抓，像素里都没有它。

这不是 CAPTUREBLT 的问题。那个标志位（capture_windows.go:169）额外包含的是 layered window（工具提示、部分悬浮层），不含光标。这是个很常见的误解，PrintWindow(PW_RENDERFULLCONTENT) 同样不包含。

4.2 要怎么修

只能自己画上去：

  1. GetCursorInfo → 拿到 hCursor、ptScreenPos 和 CURSOR_SHOWING 标志（不显示时不能画）。
  2. GetIconInfo → 拿到 hotspot。这一步容易漏：光标位置指的是它的热点（箭头尖），不是位图左上角，不减 hotspot 会整体偏移。
  3. DrawIconEx(..., DI_NORMAL) 画到内存 DC 上，必须在读 DIB 之前。

4.3 坑

  • GetIconInfo 每次都分配 hbmMask / hbmColor 两个位图，必须 DeleteObject。15fps 下每秒漏 30 个 GDI 句柄，默认上限 1 万个，几分钟就耗尽，症状是抓屏开始失败或画面花掉。这是最容易出事的地方。
  • 单色光标 hbmColor 为 NULL，DI_NORMAL 配合掩码仍然能画。
  • StretchBlt 那条分支（-scale 时走）要按缩放比例换算坐标，否则光标位置会偏。

4.4 为什么说它不是一行代码

画面里一旦有了光标，鼠标划过静止画面就会改变像素，frame_diff.go 的静止停发立刻失效。

现在这种场景带宽是 0（盯着文档时鼠标乱动不花任何流量），改完会直接顶到满帧率。

server/ws.go:496 那处注释早就写明了这一点：

GDI's BitBlt never composites the mouse cursor, so moving the pointer across a still screen leaves the pixels identical. That is why cursor motion alone sends nothing -- and why adding cursor compositing to the capture would need this comparison revisited.

所以真要做得配套决定"光标区域的差异不算变化"，否则就是拿带宽换指针。

5. 跨功能的通用教训

把上面散落的坑提炼一下：

1文档会骗人，实证不会

OpenClipboard(NULL) 有三处官方文档说必然失败。实测可用。

判断标准不是"文档怎么说"，而是失败的形态：如果它真的坏了，是响亮的（返回 0 + 用户可见的报错），那就不值得为它预先引入一个隐藏窗口 + 专用线程 + 消息循环。

2措辞为"成功"的错误最危险

Errno(0).Error() = "The operation completed successfully."，而它会原样显示给用户。

错误信息要把数字码带出来。含糊的错误让人困惑，"成功"的错误把人带向完全错误的方向。

3对称性假设必须逐个轴验证

滚轮两个轴，一个反、一个不反。想当然地"两个都翻"或"两个都不翻"都是错的。

同一类东西的不同维度，约定未必一致。

4测试自己也要被测试

证明 TestWheelDirection 有牙齿的办法，是把修复改回去，看它是不是按用户报的症状失败。

一个永远通过的测试不是保障，是装饰。

5单一的验证主体证明不了正确性

"写进去再用自己的读函数读出来一样"——只能证明自洽。

必须换一个主体：另一个进程的 Get-Clipboard，或者另一个执行环境（headless 浏览器）。

6隐藏的"单实例假设"是最贵的债

  • pendingMove / moveScheduled / dropping 都假设只有一个指针。
  • 剪贴板假设只有一个持有者（而且同进程内都不可重入）。

这些代码在只有一个人用的时候完全正确，所以不会被发现，直到第二个手指 / 第二个客户端出现。

7合并会打乱顺序

任何"延迟到下一帧再发"的优化，都必须在使用它的事件之前显式 flush。

moveTo 被 rAF 合并，click 就不会等它——点击落在指针的上一个位置。

8直觉比代码更值得怀疑

写测试时三次失败，三次都是我的断言错了、代码是对的：

  • 鼠标模式下滑动后不点击 —— 那正是触控板 tap-to-click 的行为。
  • 双指滚动只算质心位移 —— 所以单指动 50px 只滚 25px。
  • 两次手势之间必须留够双击窗口 —— 那是设计。

测试失败时，先问一句：是不是代码比我以为的更对？

9前端没有测试框架，不等于没法验证

touch.ts 的三个性质让它可以被验证，而这三个性质都是设计出来的：

  1. 不依赖 DOM → 可以在 node 里跑。
  2. 时钟由外部注入 → 计时逻辑可以用合成时间戳精确走到边界。
  3. 输出是数据（action 列表）而不是副作用 → 可以直接断言。

再往上一层，headless Chrome + CDP 用一个桩 websocket 就能覆盖真实的 DOM 事件管线，且不碰真实桌面——顺带绕开了本机的工作站焦点争用问题。

不引入测试框架，也可以有测试。
